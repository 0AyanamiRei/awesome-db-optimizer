核心思路：ORCA 是一个 Cascades 风格的优化器。 它将一条 SQL 翻译成内部表达式树，放入 Memo（DP 表）， 然后通过多阶段、Job-基于依赖图的并行搜索来探索所有等价计划空间， 最终用代价模型选出最优物理执行计划。 这份文档追踪的正是这条 "SQL 进，Plan 出" 的主路径。

Stage 0：SQL → DXL（外部）

ORCA 自身不处理 SQL 文本。SQL 解析、语义分析由 Greenplum Database (GPDB) 的 PostgreSQL 风格解析器完成。GPDB 将解析后的查询树序列化为 DXL (Data eXchange Language) —— 一种基于 XML 的中间表示， 通过进程间通信传给 ORCA。

Client SELECT ...
SQL →
GPDB Parser / Analyzer
DXL (XML) →
ORCA Optimizer
本文的关注边界：从 GPDB 传来 CDXLNode *query 开始， 到 ORCA 返回 CDXLNode *pdxlnPlan 结束。 SQL 解析 → DXL 的序列化过程不在本文范围内。

相关代码：libnaucrates/ 库定义了所有 DXL 操作符（CDXLNode、CDXLLogical*、CDXLPhysical* 等）。

Stage 2：预处理 & QueryContext

CQueryContext::PqcGenerate() 做三件事：

1. 表达式预处理

调用 CExpressionPreprocessor 对逻辑表达式做规范化：谓词下推、冗余 Join 消除、子查询提升等。这些都是逻辑→逻辑的改写，不涉及物理算子。

2. 属性推导

调用 PdpDerive() 自底向上推导关系属性 (CDrvdPropRelational)：输出哪些列、有哪些 Key、外键约束、分区信息等。

3. 包装 Required Props

从原始查询中提取"要求属性" (CReqdPropPlan)：最终结果需要哪些列、什么分布、什么排序顺序。

区分两个概念：
  • Derived Properties（推导属性）——表达式"实际具有的"属性，如输出列、键约束
  • Required Properties（要求属性）——上层对下层"要求的"属性，如"我需要按 (a) Hash 分布"
这套 Required/Derived 机制是 Cascades 框架的核心，它驱动 Enforcer（Motion/Sort 等）的自动插入。

CExpression：ORCA 的表达式树

如果目标是理解 subquery unnesting，而不是先看物理算子绑定，那么最重要的对象不是 CPhysical*，而是 CExpression。ORCA 的逻辑 rewrite、subquery→Apply、 Apply→Join 都是在 CExpression 树和后续 Memo 里的 CGroupExpression 上发生的。

这意味着一个逻辑查询在 ORCA 里不是“SQL AST”，而是下面这种统一树形对象：

CExpression 根节点

  • Pop() = CLogicalSelect
    • child[0] = CExpression
      • Pop() = CLogicalGet("students s1")
      • ...
    • child[1] = CExpression
      • Pop() = CScalarCmp(=)
      • child[0] = CScalarIdent(s1.score)
      • child[1] = CScalarSubquery
        • child[0] = CLogicalGbAgg(MAX(s2.score))

Logical

CLogical* 描述关系代数节点：Get、Select、Project、GbAgg、Join、Apply 等。

Scalar

CScalar* 描述谓词和表达式：列引用、比较、函数、聚合函数、subquery 标量节点。

Physical

CPhysical* 是后面 implementation 规则生成的执行方式；理解 unnest 之前可以先放后。

关键是：subquery 一开始常常藏在 scalar child 里，例如 Select 的 predicate 或 Project 的 scalar list。 ORCA 的 subquery handler 会把这些 scalar subquery 拆出来，把原来的 logical child 包成 Apply tree， 同时返回一个不再含 subquery 的 residual scalar。这样后续 xform 就能像处理普通逻辑树一样处理它。

Before

  • Select
    • Get(students s1)
    • ScalarCmp
      • s1.score
      • ScalarSubquery
        • GbAgg(MAX(s2.score))
          • Select[s2.major = s1.major]
          • Get(students s2)
→

After CSubqueryHandler

  • Select
    • LeftOuterApply
      • Get(students s1)

阅读重点：CExpression 是 rewrite 的载体，COperator 决定节点类型， DeriveOuterReferences() / DeriveUsedColumns() 这类属性告诉规则“这棵子树是否还读外层列”。 相关子查询能否 unnest，本质上就是能否把这些 outer references 从 RHS 中安全移走。

CExpression 与 CGroupExpression 的关系

CExpression 和 CGroupExpression 不是同一个层次的对象： 前者是一棵具体树，子节点仍然是具体 CExpression *； 后者是 Memo 里的等价类成员，子节点不再指向具体表达式，而是指向一组可替换实现的 CGroup *。

CExpression：树形表达式

Select child[0] → Join
child[1] → ScalarCmp
Join child[0] → Get(t1)
child[1] → Get(t2)
child[2] → join predicate

用于翻译、预处理、xform binding、计划提取后的物理 plan 表示。

插入 Memo →

CGroupExpression：Memo 中的表达式

Group 0 GExpr: Select[Group 1, Group 4]
Group 1 GExpr: InnerJoin[Group 2, Group 3, Group 5]
GExpr: InnerJoin[Group 3, Group 2, Group 5]

一个 Group 保存等价表达式；一个 GroupExpression 保存 operator + child groups。

因此，CExpression::m_pgexpr 是一个回指针：当某棵 CExpression 是从 Memo binding 或计划提取过程中构造出来时，它可以通过 m_pgexpr 找回来源 CGroupExpression，再访问所在 CGroup 的属性、统计信息、来源 xform 和 child groups。 普通手工构造的表达式通常没有这个来源，m_pgexpr 就是 NULL。

Memo = 一组 Group 的集合。每个 Group 包含一组逻辑上等价的 GroupExpression。 初始只有一个 GroupExpression 入组；随着 Exploration 规则被应用，每个 Group 里会不断长出等价的替代方案。

Memo / Group / GroupExpression 的组织方式

Cascades 优化器的关键不是保存“很多棵完整树”，而是把所有候选计划压缩进一个共享图结构。 ORCA 的 Memo 就是这个共享搜索空间：相同语义的子查询只存一份 Group，父表达式通过 child group 引用它们， 这样 join reorder、predicate move-around、implementation rule 产生的候选计划可以复用同一批子问题。

对象 保存什么 在搜索中的作用
CMemo 所有 CGroup，以及根 group 指针 整个优化搜索空间；负责插入、去重、合并 duplicate group、最后从 root 提取最优计划
CGroup 一组逻辑等价的 CGroupExpression，以及 group 级属性和统计信息 动态规划的子问题：优化一个 group，就是在它的所有等价表达式里找满足 required props 的最低成本实现
CGroupExpression 一个 COperator * 加一组 child CGroup * Memo 里的候选表达式；xform 以它为单位做 pattern binding、生成新表达式并插回 Memo
CCostContext 某个 group expression 在特定 required properties 下的 child contexts、cost 和 derived plan props 记录物理优化结果；同一个 group expression 在不同 required props 下可能有不同最优成本

Memo 相关对象的字段地图

如果把 CExpression 看成“树节点”，Memo 这套对象可以按下面的字段结构来记： CMemo 管全局搜索空间，CGroup 管一个等价类， CGroupExpression 管等价类里的一个候选表达式， COptimizationContext 和 CCostContext 则记录“在某组 required properties 下怎么优化、成本是多少”。

CGroupExpression 是 Memo 里的“表达式节点”。它和 CExpression 最容易混淆：两者都有 m_pop，但 CExpression 的 child 是 CExpression *，而 CGroupExpression 的 child 是 CGroup *。 这就是 Memo 能共享子问题的核心。

COptimizationContext 代表“优化某个 Group 时，父节点要求它交付什么性质”。 同一个 Group 面对不同 required properties，可能需要不同物理实现；例如一个父节点要求 hash distribution， 另一个父节点要求 sorted order，这会产生不同 context。

CCostContext 是真正记录成本的对象。它绑定的是： “某个 CGroupExpression，在某个 COptimizationContext 下， 选择哪些 child contexts，最终 cost 和 derived plan properties 是什么”。 COptimizationContext::m_pccBest 最后就会指向当前 required properties 下最好的 CCostContext。

输入 CExpression 树

  • Select
    • Join
      • Get(t1)
      • Get(t2)
    • Predicate
→

Memo DAG

  • Group 0: Select[Group 1, Group 4]
    • Group 1: Join[Group 2, Group 3]
    • Group 1: Join[Group 3, Group 2] 探索阶段新增
    • Group 2: Get(t1)
    • Group 3: Get(t2)
    • Group 4: Predicate

这个结构解释了 ORCA 为什么会频繁在 CExpression 和 CGroupExpression 之间转换： xform 需要一棵具体树来做模式匹配和构造结果，所以会从 CGroupExpression binding 出 CExpression；而搜索空间需要共享和去重，所以 xform 结果又会被重新插入 Memo， 变回新的 group 或新的 group expression。

容易混淆的一点：CGroupExpression 的 child 是 CGroup *， 不是 CExpression *。这意味着 InnerJoin[Group2, Group3] 并没有固定选择 Group2 里的哪一个实现；直到 costing / plan extraction 阶段， 优化器才会根据 required properties 和 cost context 递归选择具体物理表达式。

Stage 4：多阶段搜索

📄 libgpopt/src/engine/CEngine.cpp:1674-1740 — CEngine::Optimize()

这是整个优化器的核心循环：

void CEngine::Optimize()
{
    CJobFactory jf(m_mp, ulJobs);
    CScheduler sched(m_mp, ulJobs);
    CSchedulerContext sc;
    sc.Init(m_mp, &jf, &sched, this);

    // 按阶段逐步搜索
    for (ULONG ul = 0; !FSearchTerminated() && ul < ulSearchStages; ul++)
    {
        // 1. 为根 Group 创建 OptimizationContext
        COptimizationContext *poc = GPOS_NEW(m_mp) COptimizationContext(
            m_mp, PgroupRoot(), m_pqc->Prpp(), ...);

        // 2. 调度根 Job
        ScheduleMainJob(&sc, poc);

        // 3. ★ 运行调度器 —— 所有 Job 在此并发执行
        CScheduler::Run(&sc);

        poc->Release();

        // 4. 提取本阶段最优
        CExpression *pexprPlan = m_pmemo->PexprExtractPlan(...);
        PssCurrent()->SetBestExpr(pexprPlan);

        // 5. 阶段收尾：合并 Group、收紧代价阈值
        FinalizeSearchStage();
    }
}

4.1 Job 依赖树

ScheduleMainJob() 只做一件事：调度一个 CJobGroupOptimization（根 Group 的优化 Job）。 这个 Job 会递归地派生子 Job，形成一棵依赖树：

CJobGroupOptimization 根 Group：找到满足 Required Properties 的最优计划
派生子 Job ↓
CJobGroupExploration 探索所有逻辑等价表达式
CJobGroupImplementation 生成物理候选表达式
CJobGroupExpressionOptimization 优化每个 GroupExpression
继续展开 ↓
CJobGroupExpressionExploration 对单个 GE 做探索
CJobTransformation 应用一条具体规则
CJobGroupExpressionImplementation 对单个 GE 生成物理实现
CJobGroupOptimization 递归优化子 Group

4.2 六种核心 Job 类型

Job 类职责产生什么
CJobGroupOptimization 优化一个 Group：找到满足 Required Props 的最优计划 派生子 Job
CJobGroupExploration 对一个 Group 的每个 GE 应用 Exploration 规则 新的逻辑等价 GroupExpression
CJobGroupImplementation 对一个 Group 的每个 GE 应用 Implementation 规则 物理 GroupExpression（候选执行方式）
CJobGroupExpressionExploration 对单个 GroupExpression 应用所有匹配的 Exploration 规则 新的逻辑等价表达式入组
CJobGroupExpressionImplementation 对单个 GroupExpression 应用所有匹配的 Implementation 规则 物理候选（如 InnerJoin→HashJoin）
CJobTransformation 执行一个具体的变换规则 Binding → Transform → 新表达式入 Memo

4.3 变换规则：探索空间的核心引擎

Job 的最终执行落在 CJobTransformation 上，它执行一个具体的变换规则。规则分两类：

Exploration 逻辑→逻辑

产生逻辑等价的替代表达式，加入同一 Group。不改变语义，只改变表达形式。

例如： CXformJoinAssociativity — (A⋈B)⋈C → A⋈(B⋈C)
CXformJoinCommutativity — A⋈B → B⋈A
CXformLeftSemiJoin2InnerJoin — SemiJoin → InnerJoin + GroupBy

Implementation 逻辑→物理

将逻辑算子具体化为物理执行算子。每个逻辑算子可能对应多种物理实现。

例如： CXformInnerJoin2HashJoin → CPhysicalInnerHashJoin
CXformInnerJoin2NLJoin → CPhysicalInnerNLJoin
CXformGet2TableScan → CPhysicalTableScan

规则如何应用到表达式上

ORCA 的 rule 不是直接在 SQL 文本上运行，而是在 Memo 中的 CGroupExpression 上运行。 一个 CJobTransformation 拿到“某个 group expression + 某条 xform”，调用 CGroupExpression::Transform()，把匹配到的表达式 binding 抽出来，再调用具体 xform 的 Transform()。结果进入 CXformResult，最后插回 Memo。

所以看一条 rule，建议按下面四个点读：

问题对应源码读法
它匹配什么形状？ PexprPattern() / 构造函数中的 pattern tree 看根算子和 child 是 CPatternLeaf、CPatternTree 还是具体算子。
什么时候值得应用？ Exfp(CExpressionHandle &) 看它依赖哪些 derived properties，例如 outer refs、是否含 subquery、是否已有 required columns。
真正改了什么？ Transform(ctx, result, expr) 看它新建了哪些 CExpression，把哪些 child/标量谓词搬到了哪里。
失败怎么处理？ 返回空 result、生成 correlated apply、或保留原表达式 这点对 subquery unnest 特别重要：不是所有相关子查询都能安全变成普通 join。
和 unnest 的关系：subquery unnest 不是一个孤立函数一次做完。 它先通过 subquery handler 生成 Apply 形态，再通过 Apply2Join 类 xform 调 decorrelator。 这些步骤都作为 exploration rule 的结果进入 Memo，让后续规则继续改写。

4.4 多阶段搜索策略

ORCA 的搜索分多个 SearchStage，每个阶段控制应用哪些变换规则 + 使用什么时间/代价阈值：

Stage 1 低代价阈值
  • 只应用关键 Exploration 规则
  • 例如 Join 交换律
  • Timeout: 0.5s
  • Cost threshold: 低
→
Stage 2 放宽阈值
  • 应用更多 Exploration 规则
  • 继续扩大搜索空间
  • Timeout: 2s
  • Cost threshold: 中
→
Stage N 最终阶段
  • 应用所有规则
  • 无代价限制
  • 找到最优或超时
  • 提取阶段最优计划
设计意图：这是 ORCA 独有的"渐进式优化"策略。早期阶段以低代价阈值快速剪枝，即使丢失最优解，也能给出一个还不错的结果。后期阶段逐步放宽限制，逼近全局最优。这使得 ORCA 满足数据库"至少给出一个可行计划"的时效性要求。

4.5 并行搜索：CScheduler

CScheduler::Run() 驱动所有 Job 的并发执行。调度器维护一个可运行 Job 队列 （没有未完成依赖的 Job），多 Worker 从中取 Job 执行：

WaitQueue

有依赖未满足

  • Job-A：等待子 Job
  • Job-B：等待子 Job
  • ...
依赖完成 →

RunnableQueue

依赖已满足，Worker 可执行

  • Worker 1 → Job-X → FExecute()
  • Worker 2 → Job-Y → FExecute()
  • Worker 3 → Job-Z → FExecute()
Job::FExecuteResult
  • fCompleted=true：Job 完成，通知父 Job（引用计数 -1）
  • fCompleted=false：Job 暂停/等待子 Job，依赖的子 Job 入队
  • 根 Job 完成后，调度结束
关键设计：Job 是可重入的 (reentrant)。每个 Job 内部有一个状态机 (CJobStateMachine)， FExecute() 可能被多次调用，每次从一个"断点"继续执行。 这使得调度器可以在 Job 之间自由切换，无需 OS 线程级别的上下文切换开销。

Unnest in ORCA

这一节只看 rewrite / transform 层，不进入 Stage 5/6 的物理计划提取和 DXL 输出。 PR #19 的 unnest 文档用 students 示例解释了 2015 BTW 论文的核心直觉：相关子查询先表示成 dependent join / Apply，再把 RHS 中对外层列的依赖拉出来，必要时给聚合补 group key，最后变成普通 join。 ORCA archive 中能看到非常接近这套说法的工程实现。

示例 SQL

示范查询是“找每个专业中分数等于本专业最高分的学生”：

SELECT name, major
FROM students AS s1
WHERE score = (
  SELECT MAX(s2.score)
  FROM students AS s2
  WHERE s2.major = s1.major
);

这里的 s1.major 是内层子查询的 outer reference。直觉执行是： 对外层每个 s1 行，重新算一次“该专业最高分”。Unnest 的目标是把它改成一次关系计算： 先按 major 聚合 s2，再 join 回 s1。

SQL scalar subquery score = (SELECT MAX(s2.score) ... WHERE s2.major = s1.major)
→
CScalarSubquery 子查询先存在于 scalar child 里
→
CLogicalLeftOuterApply / CLogical*Apply 保留 RHS 读取外层列的 dependent join 语义
→
CXform*Apply2*Join
  • CDecorrelator::FProcess(inner)
  • 上拉 s2.major = s1.major
  • 补 GROUP BY s2.major
  • 生成普通 Join predicate

1. Scalar subquery 先变成 Apply

📄 libgpopt/src/xforms/CSubqueryHandler.cpp:8-23；CSubqueryHandler.cpp:2212-2237

CSubqueryHandler 的文件注释已经把职责说得很直白：给定一个 scalar child 含 subquery 的 Select / Project / GbAgg / SequenceProject，它会创建一个新的表达式：logical child 变成 Apply tree， scalar child 则变成 subquery-free 的 residual scalar。 

// CSubqueryHandler.cpp file comment
// transforming subquery expressions to Apply expressions;
// Given a SELECT/PROJECT/Gb-Agg/SEQUENCE-PROJECT expression whose scalar
// child involves subqueries, this class is used for unnesting subqueries by
// creating a new expression whose logical child is an Apply tree and whose
// scalar child is subquery-free

对于 scalar subquery，ORCA 会优先构造 outer apply：

// CSubqueryHandler::FCreateOuterApplyForScalarSubquery()
CExpression *pexprLeftOuterApply =
    CUtils::PexprLogicalApply<CLogicalLeftOuterApply>(
        mp, pexprOuter, pexprInner, colref, popSubquery->Eopid());

这一步对应 2015/PPT 里的 dependent join：左侧是外层 students s1， 右侧是内层 students s2 + filter + aggregate。Apply 节点保留了“右侧可以读左侧列”的语义。

2. Apply2Join rule 调用 decorrelator

📄 libgpopt/include/gpopt/xforms/CXformApply2Join.h:28-31；CXformApply2Join.h:133-219

CXformApply2Join 是一组 Apply→Join 规则的模板基类，注释写明： “Transform Apply into Join by decorrelating the inner side”。它的子类包括 CXformInnerApply2InnerJoin、CXformLeftOuterApply2LeftOuterJoin、 CXformLeftSemiApply2LeftSemiJoin、CXformLeftAntiSemiApply2LeftAntiSemiJoin 等。 

// CXformApply2Join::Decorrelate()
if (CUtils::FHasSubqueryOrApply((*pexprApply)[1]))
{
    // Subquery/Apply must be unnested before reaching here
    return;
}

if (!FDecorrelate(mp, pexprApply, &pexprInner, &pdrgpexpr))
{
    // decorrelation failed, create correlated apply expression if possible
    CreateCorrelatedApply(mp, pexprApply, pxfres);
    return;
}

CExpression *pexprPredicate =
    CPredicateUtils::PexprConjunction(mp, pdrgpexpr);
CExpression *pexprResult =
    GPOS_NEW(mp) CExpression(mp, GPOS_NEW(mp) TJoin(mp),
                             pexprOuter, pexprInner, pexprPredicate);
pxfres->Add(CNormalizer::PexprNormalize(mp, pexprResult));

这里有两个重要信号：

  • 内部 subquery / Apply 要先处理：如果 inner child 里还有 subquery 或 Apply，当前 Apply2Join 直接返回。这说明 ORCA archive 更偏 staged pipeline，不是 2025 论文那种 holistic 一次性全局处理所有 dependent join。
  • 失败时保留 correlated apply：decorrelation 不安全时，规则会尝试生成 CLogical*CorrelatedApply，最后在 GPDB 中可能成为 correlated join / subplan，而不是强行改成普通 join。

3. Decorrelator 把相关谓词拉上来

📄 libgpopt/src/xforms/CDecorrelator.cpp:157-187；CDecorrelator.cpp:353-390

CDecorrelator::FProcess() 的输入是 Apply 的 inner child，以及外层输出列集合 (*pexprApply)[0]->DeriveOutputColumns()。它递归处理 inner tree， 目标是产出一个不再引用外层列的 inner expression，并把被拉出来的相关谓词放进 pdrgpexprCorrelations。 

// CDecorrelator::FProcess()
if (outerRefsToRemove->IsDisjoint(pexpr->DeriveOuterReferences()))
{
    pexpr->AddRef();
    *ppexprDecorrelated = pexpr;
    return true;
}

BOOL fSuccess =
    FProcessOperator(mp, pexpr, fEqualityOnly, ppexprDecorrelated,
                     pdrgpexprCorrelations, outerRefsToRemove);

对 Select，decorrelator 会把 predicate 的 conjuncts 分成两类： 不含 outer ref 的 residual 留在 RHS；含 outer ref 且可延迟的 correlation 被上拉到 join predicate。

Inner before decorrelation
  • Select [s2.major = s1.major]
  • Get(students s2)
→
After CDecorrelator
  • inner = Get(students s2)
  • correlations += (s2.major = s1.major)
→
Apply2Join result
  • Join(Get students s1, inner subtree)
  • predicate: s2.major = s1.major AND original apply predicate

4. 聚合场景：补 group key 是语义要求

📄 libgpopt/src/xforms/CDecorrelator.cpp:411-482

students 示例的核心难点是 aggregate。原始子查询写的是一个 scalar aggregate： MAX(s2.score)。但它是在每个外层 s1.major 绑定下计算的。 一旦把多次绑定合并成一次关系计算，聚合就必须按相关列分组，否则会变成全表一个最大值。

ORCA 的 FProcessGbAgg() 正是这么做的：

// CDecorrelator::FProcessGbAgg()
// Get the columns from pexprRelational that are referenced in the pulled-up correlated
// "=" predicates in pdrgpexprCorrelations and add them to the grouping columns.
// ...
// Example:
//   select *
//   from foo
//   where foo.a in (select count(*) from bar where bar.b=foo.b)
//
// gets transformed into
//   select *
//   from foo semijoin (select bar.b, count(*) from bar group by bar.b) subq(b, cnt)
//        on foo.a = subq.cnt and foo.b = subq.b
pcrs->Intersection(pcrsOutput);
pcrs->Include(popAggOriginal->Pdrgpcr());
CColRefArray *colref_array = pcrs->Pdrgpcr(mp);
CLogicalGbAgg *popAgg =
    GPOS_NEW(mp) CLogicalGbAgg(mp, colref_array, popAggOriginal->Egbaggtype());

映射到 students 示例，就是把内侧聚合从： 

GbAgg [global]
  MAX(s2.score)
  input: Select[s2.major = s1.major](Get s2)

改成：

GbAgg [group by s2.major]
  MAX(s2.score)
  input: Get s2

Join predicate:
  s2.major = s1.major
  AND s1.score = max_score
这就是 2015 BTW 论文和 ORCA 实现最贴近的地方： 论文里说 dependent join 下推穿过 aggregate 时要把绑定域列加入 group by； ORCA 里则表现为 decorrelator 从被拉起的等值相关谓词中找 inner columns，并把它们加入 CLogicalGbAgg 的 grouping columns。

COptimizer.cpp ~Line 227

2 翻译入

CTranslatorDXLToExpr.cpp ~Line 356

3 算子体系

快速浏览 CLogical.h / CPhysical.h / CScalar.h 三个基类，建立"三层算子模型"的心智。

operators/CLogical.h, CPhysical.h, CScalar.h

4 预处理

读 CQueryContext::PqcGenerate()，理解表达式在进 Memo 之前做了什么规范化。

5 表达式树

读 CExpression.h，建立“算子 + 子表达式 + 属性缓存”的心智；这是理解 rewrite 的入口。

operators/CExpression.h

6 Memo 构建

看 CEngine::Init() → InitLogicalExpression() → PgroupInsert()，理解一棵表达式树如何拆成 Group/GroupExpression 并倒入 Memo。

7 搜索主循环

CEngine.cpp ~Line 1674

8 Job 体系

读 CJob.h（Job 基类设计思想）、然后选读 CJobGroupOptimization::FExecute() 的状态机实现。

search/CJob.h, CJobGroupOptimization.cpp

9 变换规则

读 CXform.h、CJobTransformation.cpp、CGroupExpression::Transform()，理解 pattern binding 和 result 入 Memo。

xforms/CXform.h, search/CJobTransformation.cpp, search/CGroupExpression.cpp

10 Unnest

按 CSubqueryHandler → CXformApply2Join → CDecorrelator 的顺序读，重点看 Apply 和 group key augmentation。

xforms/CSubqueryHandler.cpp, CXformApply2Join.h, CDecorrelator.cpp

11 计划提取

看 CEngine::PexprExtractPlan()，理解如何从 Memo 的 CostContext 中反序列化出最优物理计划树。

CEngine.cpp ~Line 1786

回到 CreateDXLNode() → CTranslatorExprToDXL，收束闭环。

COptimizer.cpp ~Line 320
