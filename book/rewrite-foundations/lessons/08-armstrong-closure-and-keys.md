# L08 · Armstrong 公理、闭包与键

原文：§6.1，印刷页 207–208，[PDF 第 228–229 页](../../Query%20opt.pdf#page=228)。本节逐条解释原书的三条 Armstrong 公理、三个常用派生规则、FD 闭包、超键和键。推导例子是教学展开；原书明确声明这些公理是 sound and complete。

L07 把函数依赖定义成“两条记录相同的左侧值会得到相同的右侧值”。如果已知很多 FD，优化器需要机械地推出更多结论。例如已知 `A → B` 和 `B → C`，不能每次都重新枚举关系实例；需要一套只操作属性集合的推理规则。

## 三条 Armstrong 公理

设 `A₁、A₂、A₃` 都是关系的属性集合。原书给出：

### 1. 自反律（Reflexivity）

> 如果 `A₂ ⊆ A₁`，那么 `A₁ → A₂`。

左侧已经包含右侧，当然能够决定右侧。例如 `AC → A`。这条规则不需要任何数据约束。

### 2. 增广律（Augmentation）

> 如果 `A₁ → A₂`，那么 `(A₁ ∪ A₃) → (A₂ ∪ A₃)`。

在两边同时加入同一组属性，不会破坏原来的决定关系。已知 `A → B`，就可以得到 `AC → BC`。

### 3. 传递律（Transitivity）

> 如果 `A₁ → A₂` 且 `A₂ → A₃`，那么 `A₁ → A₃`。

这正是 L07 排序例子中从 `c.id → c.nid`、`n.id → n.name` 得到更长依赖链的步骤。严格地说，连接条件负责把中间属性对应起来；FD 传递本身只处理“决定”关系。

原书称这三条规则 **sound and complete**：sound 表示推导出的每条 FD 都确实成立；complete 表示所有由给定 FD 逻辑蕴含的 FD，都可以通过这些规则推导出来。这个声明针对经典 FD 语义；遇到 NULL、bag 身份或具体算子时，要先确认语义是否仍然相同。

## 三条常用派生规则

原书还列出三个可由上述公理推出的规则，实际使用时更方便。

### Union

> 如果 `A₁ → A₂` 且 `A₁ → A₃`，那么 `A₁ → (A₂ ∪ A₃)`。

左侧同时决定两组属性，就决定它们的并集。

### Decomposition

> 如果 `A₁ → (A₂ ∪ A₃)`，那么 `A₁ → A₂` 且 `A₁ → A₃`。

这是增广律的反向拆分形式，便于把一个宽的右侧拆成多个局部结论。

### Pseudotransitivity

> 如果 `A₁ → A₂` 且 `(A₂ ∪ A₄) → A₃`，那么 `(A₁ ∪ A₄) → A₃`。

推导思路是：由增广得到 `(A₁ ∪ A₄) → (A₂ ∪ A₄)`，再使用传递律得到目标。它常用于“左侧已经能提供中间属性，但还需要保留一部分额外属性”的场景。

## FD 的闭包

给定 FD 集合 `F`，原书用 `F⁺` 表示它的**闭包**：

> `F⁺` 是使用这些推理规则可以从 `F` 推导出的全部函数依赖集合。

闭包是一个逻辑对象，不是把数据表扫描一遍得到的统计结果。实际算法通常不会真的枚举 `F⁺` 的所有元素，而是计算某个属性集合 `X` 的闭包 `X⁺`：从 `X` 出发反复应用 FD，把能够推出的属性加入集合。

例如：

```text
F = { A → B, B → C, AC → D }
X = { A, C }
```

计算 `X⁺`：

1. 初始为 `{A,C}`；
2. `A → B` 可用，加入 `B`；
3. `B → C` 已经没有新属性；
4. `AC → D` 的左侧已经包含在闭包中，加入 `D`；
5. 得到 `X⁺ = {A,B,C,D}`。

如果 `X⁺ = A(R)`，`X` 就是超键。还要检查每个属性是否可以从 `X` 中删除；如果删掉任何一个属性后都不再覆盖全部 `A(R)`，`X` 才是键。

## 一个完整的键判断

继续使用 `R(A,B,C,D)` 和：

> `A → B`
>
> `B → C`
>
> `AC → D`

对 `X=AC`：

> `AC⁺ = {A,C}`
> `→ {A,B,C}`（使用 `A→B` 和 `B→C`）
> `→ {A,B,C,D}`（使用 `AC→D`）

因此 `AC` 是超键。检查真子集：`A⁺={A,B,C}`，缺少 `D`；`C⁺={C}`，缺少 `A、B、D`。所以 `AC` 是键。

注意，若只知道 `A→B` 和 `B→C`，就不能把 `A` 说成 `R` 的键；`A⁺` 是否覆盖 `D` 需要明确的 FD 证据。

## 推理规则的使用边界

FD 公理只描述属性值之间的决定关系。它没有自动说明：

- 关系是否允许重复出现；
- NULL 应该按照哪一种相等语义比较；
- join、projection、grouping 后哪些依赖仍然保留；
- 某个 FD 是 schema 保证，还是当前实例碰巧满足。

这些问题将在下一节单独处理。尤其是“当前样例中没有违反”不能替代 schema 级约束；优化器只有在知道依赖的来源和适用范围时，才能把它用于改写。
