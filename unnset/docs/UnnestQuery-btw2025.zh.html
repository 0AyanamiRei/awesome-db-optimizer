完整翻译摘要

SQL 允许非常灵活的查询嵌套方式，其中也包括访问查询外层属性的子查询。这类相关子查询能够简化查询表述，但执行效率很低，会导致 O(n²) 的运行时间复杂度；对于大型数据库，这种代价可能高到无法接受。

因此，查询优化器会尝试对依赖查询进行去嵌套，也就是去相关。然而，现有去相关技术要么适用范围有限，要么会在相关查询反复嵌套时产生次优执行计划。本文提出一种广义的去嵌套方法：它能够处理深层嵌套的相关子查询，并可推广到包括递归 SQL 在内的复杂查询构造。该方法改善了受影响查询的渐近复杂度，因此可能带来极其显著的性能提升。

关键词：查询优化、查询去嵌套。

压缩导读1 引言

论文从 SQL 的声明式承诺讲起：用户只应描述想要什么，数据库负责选择执行方式；但复杂相关子查询经常让这种承诺失效。图 1 的查询要找出汽车市场中拥有超过 5 个、且收入超过 30 万的订单的客户。查询含两层相关子查询，规范翻译会产生嵌套依赖连接。

依赖连接右侧必须针对左侧每个元组重新求值，复杂度为 Θ(|L||R|)。论文报告，该查询在 PostgreSQL 16、TPC-H SF1 上需要 25 分钟以上；人工把子查询解耦后则能很快完成，但这种改写理应由 DBMS 自动完成。

作者随后回顾 2015 版方法：它不匹配 SQL 文本模式，而是在代数层构造无重复绑定域 D，再把由 D 驱动的依赖连接向下推。该方法已被多个系统采用，但实践暴露出两个缺口：

  1. 递归 SQL、复杂 ORDER BY/GROUP BY 等高级构造没有被完整覆盖。
  2. 多个依赖连接层层嵌套时，自底向上逐个消除会扩大早先步骤的工作量；嵌套越深，问题越严重。

2025 版对应提出两项改进：用整体式、自顶向下的算法联合处理嵌套依赖连接；并补齐递归 SQL、共享 CTE、全外连接谓词和逐绑定 Top-N 等构造。

2 背景

摘要2.1 问题定义

本节沿用 2015 版符号：依赖连接让左侧属性在右侧可见；𝒜(T) 表示表达式 T 产生的属性，ℱ(T) 表示其中尚未绑定的自由变量。若 ℱ(T) 非空，表达式不能独立求值。

L ⧑ R ≡ L ⋈ R　当　𝒜(L) ∩ ℱ(R) = ∅

去嵌套问题因此表述为：给定含依赖连接的关系代数表达式，把它改写成语义等价且不含依赖连接的表达式。

摘要2.2 自底向上去嵌套

这部分是对 2015 算法的重述：

  1. 先尝试简单去嵌套，把只是语法位置造成的相关谓词移动到连接条件。
  2. 若仍有依赖，从外侧投影自由变量的不同绑定，形成无重复域 D。
  3. 把由 D 驱动的依赖连接穿过选择、连接、分组等算子，直到它变成普通连接。
  4. 如果等值条件提供了替代列，可选地用 map 算子消除 D；是否这样做由连接选择性决定。
L ⧑ R ≡ L ⋈natural D (D ⧑ R)，　 D := Π𝒜(L) ∩ ℱ(R)(L)

这个过程概念上能够消除任意依赖连接，但“每次从最深处开始、一次只处理一个连接”的调度策略存在病理情况。

重点翻译2.3 自底向上方法的局限

自底向上方法对大多数查询都工作良好，但会在某些边界情况下退化。最初向作者报告这个问题的是 Sam Arch；他把复杂 UDF 翻译成纯 SQL，在这类查询中，依赖子查询可能像图 1 那样相互嵌套。论文用下面这个缩小后的变体说明问题。为了在小例子中触发缺陷，作者额外加入了相关条件 T3.a = T1.a。

算法首先消除较低的依赖连接。优化器很可能保留下面这个绑定域，而不是做列替换，因为过滤条件 T2.a = T1.a 可能具有较高选择性：

ΠT2.b(σT2.a = T1.a(T2))

问题出现在第二次运行算法、继续消除最上层依赖连接时。此时，较低连接右侧在概念上会针对 T1.a 域与 T2.b 域的完整笛卡尔积求值，而不是只针对 T1 与 T2 实际连接结果中出现的绑定组合求值。

最终结果仍然正确，因为更高处的连接条件会过滤掉不满足 T2.a = T1.a 的 T1.a 组合；但过滤发生得太晚，分组算子已经处理了大量根本不可能进入结果的值。

嵌套越深，这个问题越严重。Sam Arch 提供的真实查询名为 crash.sql，其中包含六层嵌套连接。旧策略产生多个巨大的中间笛卡尔积；这些组合随后虽然都会被过滤掉，却已经消耗了内存和 CPU。这个案例促使作者开发一种同时考虑全部依赖连接的整体式方法，从根源上避免无效域的交叉相乘。

3 Holistic Query Unnesting

本节介绍一种 holistic unnesting algorithm，它在一次遍历中共同处理嵌套的 dependent joins。可以将其视为 [NK15] 的一个 top-down 变体，因为它采用了相同的思想：将 free variable bindings 的 domain D 向下推。不过，我们采用了不同的表述方式：算法并不将 D 显式地沿树向下推，而是记住需要加入哪个 D，并在一次 top-down 遍历中重写所有算子，直到 D 不再需要，或者可以安全地加入。

我们将算法分成三个部分：首先是一个准备阶段，识别所有 non-trivial dependent joins，并为它们标注主算法所需的信息；其次是消除 dependent joins 的逻辑，这是主算法，会按 top-to-bottom 的顺序对所有 non-trivial dependent joins 调用；第三部分是各个算子的 unnesting rules。需要说明的是，受篇幅所限，我们没有在此给出该方法的形式化描述；形式化定义和正确性证明可以在技术报告 [Ne24] 中找到。

3.1 识别 Non-Trivial Dependent Joins

首先，我们需要识别所有 non-trivial dependent joins，也就是右侧访问了左侧所提供属性的 dependent joins。最容易实现这一点的方法是使用 indexed algebra [FMN23]，它允许我们查询 algebra expressions 的结构。如果具备这一功能，我们就考察每一次列访问，计算访问该列的算子 ◦1 与提供该列的算子 ◦2 的 lowest common ancestor（LCA）。如果 LCA 不是 ◦1 本身，它就必然是一个 dependent join ⧑3；我们为 ⧑3 添加标注，记录 ◦1 正在访问 ⧑3 的左侧。上一节示例查询的标注如图 2 所示。没有 accessing operators 的 dependent joins 是 trivial 的，可以直接转换为 regular joins。

Indexed algebra 很适合这个阶段，因为它无需任何额外的数据结构，就能在 O(log n) 时间内完成每次 LCA 计算。如果 DBMS 不支持这一功能，也可以通过追踪树中不同部分的可用列集合来计算相同的信息，只是其渐近复杂度会更差。

3.2 消除 Dependent Joins

识别出所有 non-trivial dependent joins 之后，我们按 top-to-bottom 的顺序处理它们，逐个将其消除。如果一个 dependent join 嵌套在另一个 dependent join 中，它通常会在其祖先 join 被消除时一并消除。不过，情况并非总是如此：正如下文将看到的，消除祖先 join 的过程可能在到达后代 join 之前就停止。但我们绝不会把不同的 D 集合推过 dependent joins，因此消除了第 2.3 节讨论的问题。

在贯穿本文的示例中，我们会从 ⧑1 开始，首先尝试 simple dependent join elimination。这是对 [NK15] 中 simple unnesting 的推广，如图 3 所示：我们检查所有正在访问 join 左侧的算子 op，并检查从该算子到 join 的路径是否仅由 linear operators 构成，即允许对其输入进行分区的算子，参见 [G.20]。使用 indexed algebra 可以在 O(log n) 时间内完成这个检查；否则，也可以从 op 到 join 做一次线性遍历。如果条件成立，我们就可以将 op 向上移动到 join。若 op 是一个 selection，我们就在允许的情况下将它合并进 join，从而消除这个 accessing operator。对于 map（有时也称为 projection），我们不能直接将其删除，但可以检查是否能将它移动到 join 上方。如果可以，就进行这样的移动，同样将该算子从 accessing operators 列表中移除。如果之后不再剩下任何 accessing operator，就可以直接将 dependent join 转换为 regular join。对于第 2.2 节的 EXISTS 查询，这一步已经足够；但在贯穿本文的示例中，没有一个 dependent join 能以这种方式消除。

如果 simple unnesting 不足以完成任务，就启动完整的 unnesting algorithm。它必须重写 dependent join 的右侧，使其中不再出现来自外侧的引用。为此，它维护如图 4 所示的状态。状态分为始终保持不变的部分（UnnestingInfo），以及在查询的不同部分中发生变化的部分（Unnesting）。全局部分存储 join 本身、outer references 集合，也就是左侧被右侧访问的那些列，以及对应的 domain computation D。parent 字段使算法能够识别嵌套的 dependent joins。在查询片段的局部部分，它维护一个 union-find 数据结构 cclasses，用于追踪 equivalent columns。我们利用它进行传递推理。如果查询包含形如 a = b 和 b = c 的谓词，并且存在对 c 的 outer reference，那么当 a 可用时，就可以用 a 替换它。如果我们已经用其他列替换了某个 outer reference，就把这一关系存入 repr，从而能够查到该 outer reference 的新名称。

重点翻译4 处理复杂 SQL 构造

第 3 节规则足以处理大多数查询，但全外连接条件中的相关子查询、WITH RECURSIVE、共享 CTE 和 ORDER BY ... LIMIT 都需要额外处理。它们构成 2025 版相对于 2015 版的第二项主要贡献。

4.1 全外连接条件中的相关子查询

SQL 允许连接条件访问连接两侧的列，也允许在任意表达式中放置子查询。因此，连接条件中的子查询可能同时引用左右输入。对于内连接或左外连接，可以把子查询 cross apply 到右输入后正常去嵌套；右外连接可以交换两侧。全外连接更复杂，因为输入随外层绑定变化时，“未匹配元组”应如何计算并不直接明确。

论文的变换分别构造左右输入所需的绑定域 DR 和 DS：

  1. 针对 DR × DS 的每一种可能绑定计算一次子查询谓词，并把结果保存为布尔列 m。
  2. 先用左外连接把 S 接回谓词结果，确保来自 S 的未匹配元组总共只产生一次，而匹配元组按 R 的外层绑定产生。
  3. 再用全外连接接回 R，得到最终匹配行与未匹配行。

实现时不必真的构造整个 DR × DS 子计划再重新去嵌套；可以直接对原子查询调用 unnest，使用稍作修改的 UnnestingInfo 表示组合域，并向两层连接补充对应的 IS NOT DISTINCT FROM 条件。

4.2 去嵌套 WITH RECURSIVE

论文假定递归 CTE 被翻译成 iterate 算子以及读取上一轮结果的 iterationscan：iterate 左侧计算种子，右侧重复执行直到为空。

去嵌套时，递归过程必须针对每一种外层绑定分别执行。为此，把外层引用加入递归 CTE 的列，相当于让递归按这些绑定值分区。算法还把当前递归的全部 iterationscan 加入访问列表，以确保遍历一定抵达这些扫描并给它们补上绑定列。

unnest(iteration):
  把访问点分到种子侧和递归侧
  把当前 iteration 的所有 iterationscan 标为递归侧访问点

  先 unnest 种子侧：
    重写种子输出列
    把 outerRefs 的替代列加入 iteration.leftColumns

  再 unnest 递归侧：
    把 outerRefs 的替代列加入 iteration.rightColumns

unnest(iterationscan):
  对每个 outerRef：
    找到种子输入中对应的绑定列
    把它作为 iterationscan 的新输出列
    更新 repr

先处理种子侧很重要，因为递归侧需要知道新增列及其映射。最终，每个外层绑定都拥有自己独立推进的递归状态。

4.3 去嵌套共享 CTE

共享 CTE 会把代数结构从树变成 DAG。同一个相关选择可能从连接左右两条路径抵达，于是访问列表无法简单地分到左右两侧；若直接按树算法执行，还可能把共享子计划去嵌套两次，重复插入域扫描。

解决办法是把 DAG 切成一组树，使每个共享算子成为独立子树的根，共享读取成为相邻树的叶子。收集访问点时：

  • 如果访问算子和依赖连接在同一棵树中，按普通规则记录。
  • 如果跨越共享边界，就把所有共享读取视为访问点，并继续递归分析共享定义。
  • 指定一个共享读取负责在遍历到达时触发共享定义的去嵌套，其余读取只消费改写结果。

这样，共享部分只改写一次，也只加入一次绑定域。

4.4 去嵌套 ORDER BY LIMIT

相关子查询中的 LIMIT 或 OFFSET 必须针对每一种外层绑定分别执行，不能在去嵌套后变成一次全局限制。Umbra 的排序算子原生支持分区 Top-N；其他系统可以把子查询：

SELECT *
FROM S
ORDER BY x
LIMIT l OFFSET o

改写为窗口查询：

SELECT *
FROM (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY 外层绑定列
           ORDER BY x
         ) AS rn
  FROM S
) q
WHERE rn BETWEEN o + 1 AND o + l

之后只需由窗口算子规则把外层引用加入 PARTITION BY，就能保证每个绑定拥有自己的排序、偏移和限制。

重点翻译5 评估

查询去嵌套通过消除依赖连接的二次复杂度改善渐近性能。作者指出，只要不断扩大数据集，就很容易制造任意大的加速比，因此传统性能实验的解释价值有限；本节主要展示新算法是否能够避开旧算法的灾难性计划。

压缩导读6 相关工作

早期方法直接在 SQL 表示上匹配特定模式，易于理解和集成，却无法覆盖所有情况。Kim 的早期规则还存在著名的 count bug：空输入上的聚合可能得到错误结果，后来由 Kiessling 修正。此后虽然不断增加特例规则，仍没有形成完整覆盖。

Magic Sets 通过外层绑定域和半连接减少依赖执行工作量，与本文的 D 很相似，但没有给出彻底消除依赖连接的机制；后续方法能消除某些含聚合的依赖连接。作者把 2015 版定位为第一套概念上完整的通用方案，而 2025 版负责修复嵌套连接的计划爆炸，并补齐复杂 SQL 构造。

论文还强调了一个新的现实动机：越来越多 SQL 由程序自动生成。例如 Apfel 可以把过程或 UDF 编译为纯 SQL；这种路线能避免专用过程语言实现，甚至可能更快，但前提是数据库能够可靠地消除生成查询中的深层相关性。

摘要7 结论

2025 版把先前的自底向上去相关扩展为整体式、自顶向下的方法，能够正确联合处理嵌套依赖连接，并覆盖更广的 SQL 构造。该方法已经集成到 Umbra。作者希望 DuckDB、PostgreSQL 等系统后续采用。
