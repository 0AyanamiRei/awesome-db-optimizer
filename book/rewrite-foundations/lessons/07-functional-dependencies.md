# L07 · X → Y 究竟约束什么

原文：第 6 章引言与 §6.1 开头，印刷页 207，[PDF 第 228 页](../../Query%20opt.pdf#page=228)。SQL 查询、FD 定义和依赖来源来自原文；示例数据、练习表和误区清单是教学补充。本节假设所有属性都不含 NULL，含 NULL 的情况见 L09。

> **本节回答三个问题**
>
> 1. 原书的排序例子为什么能删掉一个排序键？
> 2. `A₁ → A₂` 的精确定义怎么读？
> 3. 优化器凭什么相信一条 FD 一直成立？

## 1. 从一个排序例子开始（原文）

```sql
SELECT c.id, n.name
FROM customers AS c, nations AS n
WHERE c.nid = n.id
ORDER BY c.id, n.name;
```

原书说：`ORDER BY` 可以简化为 `ORDER BY c.id`，结果不变。理由是一条三步链：

| 步骤 | 事实 | 依据 |
| --- | --- | --- |
| ① | `c.id` 决定 `c.nid` | `c.id` 是 customers 的键 |
| ② | `c.nid` 与 `n.id` 取值相同 | 连接条件 `c.nid = n.id` |
| ③ | `n.id` 决定 `n.name` | `n.id` 是 nations 的键 |
| ⇒ | `c.id` 决定 `n.name` | 把 ①②③ 串起来 |

先用一份小数据看清楚（教学补充）：

| customers: `id` | `nid` |
| --- | --- |
| 10 | 1 |
| 11 | 1 |
| 12 | 2 |

| nations: `id` | `name` |
| --- | --- |
| 1 | China |
| 2 | France |

连接后的结果：

| `c.id` | `n.name` |
| --- | --- |
| 10 | China |
| 11 | China |
| 12 | France |

`ORDER BY c.id, n.name` 的含义是：先按 `c.id` 排；只有 `c.id` 相同的行，才用 `n.name` 决出先后。可是 `c.id` 相同的行，`n.name` 一定也相同，第二个排序键永远不会被用到，所以可以删掉。

反过来就不行。`ORDER BY n.name, c.id` 中的 `c.id` 不能删：两个 China 行需要靠 `c.id` 排出 10、11 的先后。原因是 `n.name` **不**决定 `c.id`。FD 是有方向的。

## 2. 精确定义（原文）

原书把这种关系称为**函数依赖**（functional dependency，FD），并给出定义。先认识几个记号：

| 记号 | 含义 |
| --- | --- |
| $R$ | 一个关系，可以先理解为一张表 |
| $A(R)$ | $R$ 的全部属性（列） |
| $A_1, A_2 \subseteq A(R)$ | 两组属性，每组可以有多列 |
| $t_1, t_2$ | $R$ 中的两条记录（tuple） |
| $t.A_1$ | 记录 $t$ 在 $A_1$ 这些列上的值 |

关系 $R$ 满足函数依赖 $A_1 \to A_2$，当且仅当：

$$
\forall t_1, t_2\;\big([\,t_1 \in R \land t_2 \in R \land t_1.A_1 = t_2.A_1\,] \Rightarrow [\,t_1.A_2 = t_2.A_2\,]\big)
$$

逐段读：

- $\forall t_1, t_2$：任取两条记录，不能漏掉任何一对；
- $t_1 \in R \land t_2 \in R$：两条都来自 $R$；
- $t_1.A_1 = t_2.A_1$：它们在 $A_1$ 的**每一列**上都相同；
- $\Rightarrow [\,t_1.A_2 = t_2.A_2\,]$：那么它们在 $A_2$ 的每一列上也必须相同。

一句话：**左边相同，右边就必须相同。** 写成检查程序就是：

```text
for 每一对记录 (t1, t2) in R:
    if t1[A1] == t2[A1] and t1[A2] != t2[A2]:
        违反 A1 → A2
```

“函数”一词的意思是：把 $A_1$ 的值看作输入、$A_2$ 的值看作输出，同一个输入只能有一个输出。并不需要真有一个 SQL 函数。

## 3. 动手检查（教学补充）

| `emp` | `dept` | `mgr` |
| --- | --- | --- |
| e1 | D1 | Ann |
| e2 | D1 | Ann |
| e3 | D2 | Bob |

| FD | 是否满足 | 理由 |
| --- | --- | --- |
| `emp → dept` | 满足 | 每个 emp 只出现一次，不存在左边相同的两行 |
| `dept → mgr` | 满足 | 两行 D1 都是 Ann |
| `dept → emp` | 违反 | 两行 D1 分别是 e1、e2 |
| `{dept, mgr} → emp` | 违反 | (D1, Ann) 对应 e1、e2 |
| `mgr → dept` | 这份数据满足 | 但如果明天 Ann 兼管 D3，就会被违反 |

最后一行引出下一节的关键区别。

## 4. 三个常见误区

**误区一：左边必须唯一。** 不对。`dept → mgr` 成立，而 D1 出现了两次。FD 只要求“同一个左值不能配两个不同的右值”。

**误区二：FD 可以反过来用。** 不对。`emp → dept` 成立，`dept → emp` 不成立。回到原书例子：客户编号决定国家名，国家名不决定客户编号。

**误区三：数据里没有反例，FD 就成立。** 检查数据只能说明**这一份数据**满足它。优化器改写的是查询，要对所有合法数据都正确，所以它必须知道 FD **为什么**一直成立。

## 5. FD 从哪里来（原文）

原书给出两个来源：

- **基础表**：从 schema 推出，特别是键约束和 check 条件。例如声明 `c.id` 为主键，就得到 `c.id` 决定 customers 的全部列。
- **中间结果**：代数算子会带来额外的 FD。例如排序例子中的连接条件 `c.nid = n.id` 让这两列在结果中取值相同。原书把这部分留到 §6.3，但那一节只有占位（见 L09）。

## 小结与自测

- FD $A_1 \to A_2$：任意两条记录在 $A_1$ 上相同，就在 $A_2$ 上相同。
- 有方向，不要求左边唯一，也不能只凭一份数据来确认。
- 优化器使用的 FD 来自 schema 约束和算子语义。

**自测**：在上面的 emp 表中加入一行 `(e4, D2, Ann)`，下列哪些 FD 还成立：`dept → mgr`、`mgr → dept`、`emp → dept`？
