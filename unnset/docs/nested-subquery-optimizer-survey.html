TiDB、GPORCA、DataFusion 嵌套子查询优化调研

这份报告围绕“嵌套子查询 / correlated subquery / dependent join unnesting”展开， 对比三个本地开源项目是否支持相关子查询优化，以及它们和 2015、2025 两篇 unnesting 论文之间的关系。

调研日期：2026-07-03 范围：本地源码 checkout 重点：相关子查询、Apply、聚合 decorrelation、holistic unnesting
核心结论 判断方法 三项目总览 TiDB GPORCA DataFusion 和论文的对应关系 阅读建议

核心结论

短答案：TiDB、GPORCA、DataFusion 都支持一定范围内的嵌套 / 相关子查询优化； 三者都能在源码中看到和 2015 论文、课程 PPT 中相近的工程套路； 但在本地源码中，没有找到三者实现 2025 论文提出的 “同时考虑所有 dependent joins 的 holistic unnesting”算法的证据。

最像课程/PPT术语：GPORCA

GPORCA 明确把子查询变成 Apply，再通过 xform 和 decorrelator 尝试把 Apply 变成 Join。 如果你想看“dependent join → join”的优化器实现骨架，它是三个里面术语最贴近论文的一份。

最适合读代码学习：DataFusion

DataFusion 的 Rust 代码把“拉起相关谓词、补 group by key、处理 count bug、转换为 join”写得比较集中， 读起来比生产级大型 C++/Go 优化器更直接。

生产系统风格：TiDB

TiDB 有 LogicalApply、PhysicalApply 和 DecorrelateSolver， 能 decorrelate 一批常见模式，也会在不安全或受 hint 影响时保留 Apply 执行路径。

这里的“没有找到 2025 holistic 实现”不是说这些项目永远不会做类似优化； 它只表示在当前本地 checkout 中，没有看到一个全局收集多层 dependent join、 再一次性规避绑定域乘积膨胀的专门算法。

判断方法

这次不是只搜索“subquery”关键字，而是按论文里的几个核心概念去源码里找对应物。 判断一个系统是否接近 2015/PPT 的传统 unnesting，主要看下面这些迹象：

  • 是否有 Apply / dependent join / outer reference 这样的内部表示。
  • 是否能把相关谓词从子查询内部拉出来，变成普通 join predicate。
  • 遇到聚合时，是否把相关列补进 group by key，再 join 回外层。
  • 是否处理 scalar aggregate 的空输入语义，例如 COUNT(*) 在空组上的特殊值。
  • 是否有失败回退路径：不能安全 decorrelate 时仍保留相关执行或原始子查询形态。

判断一个系统是否接近 2025 论文的 holistic unnesting，则标准更苛刻：

  • 优化器需要识别一棵查询里的多个 dependent joins，而不是只处理当前局部 Apply。
  • 需要把多层绑定关系作为一个整体建模，例如绑定列之间的真实 join domain，而不是简单保留局部 domain。
  • 需要有显式策略避免 D1 × D2 × ... 这类中间绑定域膨胀。
  • 源码或测试应体现“同时考虑多个 dependent joins”的算法入口，而不是固定顺序、递归或规则式逐层处理。
SQL 子查询 WHERE / SELECT / EXISTS / IN 中含外层引用
→
Apply / 外部引用 表达 dependent join
→
局部 decorrelate 拉谓词、补 group key、改 join

2015/PPT 路线通常可以理解成上面这条链路。2025 论文关心的是： 当一棵查询里有多层 Apply 时，不能只机械地从内到外做局部链路， 而要把所有 dependent joins 的绑定关系一起看。

TiDB

TiDB 的相关子查询支持是典型的生产优化器形态：逻辑层用 Apply 表示相关执行关系， 优化阶段尝试 decorrelate；如果不能安全转换，物理层仍可以保留 Apply 作为执行路径。

支持什么

TiDB 能处理常见的相关 EXISTS、IN、scalar subquery，以及带聚合的相关子查询。 在测试数据中可以看到有些 correlated subquery 被转成 HashJoin / HashAgg， 也可以看到某些复杂或不适合转换的查询仍保留 Apply。

这很像课程 PPT 中的“dependent join 能消掉就消掉，不能消掉就保留相关执行”。 生产系统不能只追求形式上消掉 Apply，因为 SQL 的三值逻辑、空输入聚合、outer join 语义和 hint 都会影响安全性。

和 2015/PPT 的关系

TiDB 的实现可以对应到 2015/PPT 的几个动作：

  • Apply 表示相关子查询。
  • Selection 下推/拉起后，把相关谓词变成 Join predicate。
  • Projection 里替换 correlated column，修复列引用。
  • Aggregation 场景把相关绑定列补进 group by，必要时给外层列加 firstrow。
  • 处理 COUNT、默认值和 HAVING 语义，避免“等价变换”破坏 SQL 结果。

和 2025 论文的关系

没有找到 holistic unnesting 的实现痕迹。TiDB 的 decorrelation 是一个 optimizer rule， 递归处理当前 Apply 及其子树；这不等于 2025 论文里“同时看所有 dependent joins， 避免多层绑定域乘积膨胀”的算法。

GPORCA

GPORCA 是三个项目中最贴近论文语言的。它有明确的 Apply 表达式族， 子查询处理器会把 scalar、existential、quantified subquery 转成 Apply 形态， 然后由 Apply-to-Join transformation 和 decorrelator 尝试去相关化。

支持什么

GPORCA 覆盖的子查询类型很广，包括 scalar subquery、EXISTS、 NOT EXISTS、ANY、ALL、多层相关子查询以及部分不可 decorrelate 场景。 这可以从 CSubqueryHandlerTest.cpp 的测试命名中直接看出来。

和 2015/PPT 的关系

如果用课程 PPT 的图来映射，GPORCA 的结构几乎可以直接翻译： 子查询先变成 Apply；Apply 的右侧如果有外层列引用，decorrelator 把相关 predicate 提出来； 右侧有聚合时补 group key；最后生成普通 Join 或保留 correlated Apply/subplan。

它对 quantified subquery 的处理也体现了工程系统的复杂性： ANY、ALL、NOT IN 等并不只是一个 semi join， 还要考虑 NULL 和空结果带来的真假值差异。

和 2025 论文的关系

没有找到 2025 holistic unnesting 的实现。一个很强的反证是： CXformApply2Join 中的逻辑要求 inner child 里仍有 Subquery/Apply 时先不做当前 Apply2Join， 也就是仍偏向“先把内部子查询 unnested，再处理当前 Apply”的 staged pipeline。

此外，本地仓库是 gporca-archive，HEAD 时间是 2023-08-30， 时间上也早于 2025 论文。除非存在另一个未在本地 checkout 中的后续分支，否则不能说它实现了该论文算法。

DataFusion

DataFusion 没有像 GPORCA 那样把“Apply”作为显眼的中心概念， 但它通过 outer reference、subquery rewrite、lateral join decorrelation 等 optimizer rule 支持相关子查询去相关化。代码较新，也比较适合作为学习材料。

支持什么

DataFusion 支持把相关 predicate subquery 转成 semi/anti/mark join； 把 correlated scalar subquery 转成 left join 加聚合； 也支持从 LATERAL join 中抽取相关 filter，必要时把 ungrouped aggregate 改为按相关列分组。

测试里有 recursive subqueries 的 TPC-H 风格例子： customer 外层、orders 中层、lineitem 内层。 优化后的形态是多个 join 和 aggregate 的组合。这说明它能处理多层相关子查询的一些常见形式。

和 2015/PPT 的关系

DataFusion 的代码非常适合映射到课程 PPT：

  • PullUpCorrelatedExpr 对应“把 RHS 中依赖 LHS 的 filter 拉出来”。
  • Aggregate 分支把相关列补到 group expressions，对应“按绑定列分组再 join 回外层”。
  • __always_true 这样的 indicator 对应“修复 scalar aggregate 空输入语义”。
  • Predicate subquery 转 semi/anti/mark join，对应 EXISTS/IN/NOT IN 的关系代数改写。

和 2025 论文的关系

没有找到 holistic unnesting 的实现。DataFusion 有 recursive subquery 测试， 但源码中最关键的限制是嵌套 Subquery 被当作 scope boundary； 这说明它不是把所有层的 dependent joins 先收集起来再统一选择绑定域。

2025：没有看到 holistic 绑定域优化

我们前面学习 2025 论文时重点讨论的是这种坏情况： 如果查询有多层相关子查询，并且内层还引用了更外层列， 从内到外逐个消 dependent join 可能会让优化器过早保留一个局部绑定域。 等外层再 unnest 时，这些局部绑定域可能被组合成比真实 join 域大得多的中间关系。 

真实需要的绑定域：
  (T1 与 T2 在相关条件下真的能配对的那些 (T1.a, T2.b))

坏的逐层近似可能得到：
  distinct(T1.a) × distinct(T2.b)

差异：
  前者受 T1/T2 的真实 join 选择性约束；
  后者像笛卡尔积一样把本来不会同现的绑定组合也放进中间结果。

三个项目都能在局部处理“把相关列加入 group by”这种传统动作。 但 2025 论文要解决的问题不是“会不会补 group by key”，而是“多层 dependent joins 的 group key / binding domain 应该一起选择，避免内层先生成过大的局部 domain”。 从本地源码看，三者都没有一个明显的全局 dependent-join graph 或 holistic rewrite pass。

传统局部处理

  1. 看到当前 Apply。
  2. 处理右侧 Selection / Projection / Aggregate。
  3. 把当前相关列加入 join predicate 或 group key。
  4. 递归或按规则继续处理下一层。

2025 期待看到的处理

  1. 先识别整棵查询中的多个 dependent joins。
  2. 分析所有外层引用和层间 join 条件。
  3. 用整体绑定关系决定哪些 domain 真的需要物化。
  4. 生成避免无效 cross product 的 unnesting 计划。

项目差异

为什么说 GPORCA 最像论文？

因为它的优化器模型本来就是 transformation-driven： 子查询被转成 Apply，Apply 再被 xform 变成 Join。 读它时，你会反复看到 Apply、Decorrelator、correlations、group columns 这些和论文/ppt 对得上的词。

为什么说 DataFusion 更适合初学者读？

DataFusion 的代码量和抽象层级相对可控。 例如 decorrelate.rs 里直接能看到 pull-up correlated expr、 aggregate 补 group by、count bug indicator 等逻辑。 如果你现在还在建立直觉，它比直接读 GPORCA C++ transformation framework 更容易先跑通脑内模型。

为什么 TiDB 显得“没有那么论文式”？

TiDB 的代码目标是服务生产优化器。 它当然有 Apply 和 decorrelate，但周围混着 schema、hint、join type、统计信息、列裁剪、物理执行等大量工程约束。 所以它很适合看真实系统如何把论文思路落地，但不一定最适合第一次理解算法本身。

阅读建议

  1. 先读 DataFusion： datafusion/optimizer/src/decorrelate.rs、 scalar_subquery_to_join.rs、 decorrelate_predicate_subquery.rs。 目标是把“相关谓词上拉、聚合补 group key、count bug”这三件事看懂。
  2. 再读 TiDB： pkg/planner/core/rule_decorrelate.go 和 logical_apply.go。 目标是理解生产系统怎样决定哪些 Apply 能消、哪些要保留。
  3. 最后读 GPORCA： CSubqueryHandler.cpp、CDecorrelator.cpp、 CXformApply2Join.h。 目标是把 transformation framework 下的 Apply-to-Join 过程和论文术语对起来。

如果你的学习目标是“验证 2025 论文的新算法有没有被工业系统采用”， 这三个本地项目目前给出的答案偏否定：能看到传统 decorrelation 很多痕迹， 但看不到 holistic all-dependent-joins simultaneous unnesting 的完整实现。
