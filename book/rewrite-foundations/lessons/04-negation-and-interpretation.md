# L04 · 否定为什么会交换 UNKNOWN 的解释

原文：§5.3 Three-Valued Logic，印刷页 203–204，[PDF 第 224–225 页](../../Query%20opt.pdf#page=224)，重点是图 5.5 和式 (5.1)–(5.8)。本节把三值求值、UNKNOWN 的解释和否定之间的关系完整展开。原书式 (5.1)–(5.4) 的第二个下标疑似误印为 `p₁`；这里按真值表使用 `p₂`，具体边界记录见 [B02](../boundaries.md#b02--unknown-解释公式的下标疑似笔误)。

上一节把一个条件的处理分成了两个阶段：先按三值逻辑求出 TRUE、FALSE 或 UNKNOWN，再根据使用位置决定 UNKNOWN 如何被接受。本节要解决的问题是：如果把“UNKNOWN 当作 FALSE”或“UNKNOWN 当作 TRUE”的解释提前，能不能把它推到表达式内部？答案是可以，但遇到否定时，解释的种类必须交换。

## 先看 AND 和 OR

先记住两种解释操作：

- `⌊p⌋⊥`：把 `p` 的 UNKNOWN 解释为 FALSE；
- `⌈p⌉⊥`：把 `p` 的 UNKNOWN 解释为 TRUE。

它们只改变 UNKNOWN，已经是 TRUE 或 FALSE 的结果保持不变。对 AND 和 OR，解释可以分别下推到两个操作数：

> `⌈p₁ ∧ p₂⌉⊥ ≡ ⌈p₁⌉⊥ ∧ ⌈p₂⌉⊥`
>
> `⌊p₁ ∧ p₂⌋⊥ ≡ ⌊p₁⌋⊥ ∧ ⌊p₂⌋⊥1`
>
> `⌈p₁ ∨ p₂⌉⊥ ≡ ⌈p₁⌉⊥ ∨ ⌈p₂⌉⊥`
>
> `⌊p₁ ∨ p₂⌋⊥ ≡ ⌊p₁⌋⊥ ∨ ⌊p₂⌋⊥`

为什么这几条成立？以第一条为例。三值真值表中，`p₁ ∧ p₂` 只有在两个输入都是 TRUE 时为 TRUE。把 UNKNOWN 解释成 TRUE 后，左侧是否为 TRUE，正好等于先把每个输入的 UNKNOWN 解释成 TRUE，再用普通二值 AND。把 UNKNOWN 解释成 FALSE 的 AND、以及 OR 的三条式子可以用同样的方式逐行检查。

这里的“等价”仍是三值表达式的等价：对所有允许输入，左右两边在解释后产生相同的 TRUE 或 FALSE。它不是说可以任意改变表达式的求值顺序。

## 否定会交换解释

否定本身把 TRUE 和 FALSE 互换，但 UNKNOWN 否定后仍是 UNKNOWN。于是解释操作穿过否定时，原来的解释方向必须交换。图 5.5 的关键关系是：

> `⌈¬x⌉⊥ ≡ ¬⌊x⌋⊥`
>
> `⌊¬x⌋⊥ ≡ ¬⌈x⌉⊥`

把 `x` 分别取 TRUE、FALSE、UNKNOWN，就可以完整核对第一条：


| `x`     | `¬x`    | `⌈¬x⌉⊥` | `⌊x⌋⊥` | `¬⌊x⌋⊥` |
| ------- | ------- | ------- | ------ | ------- |
| TRUE    | FALSE   | FALSE   | TRUE   | FALSE   |
| FALSE   | TRUE    | TRUE    | FALSE  | TRUE    |
| UNKNOWN | UNKNOWN | TRUE    | FALSE  | TRUE    |


第二条只需把两种解释的角色交换：`x=UNKNOWN` 时，左侧先得到 UNKNOWN，再按 FALSE 解释为 FALSE；右侧先把 UNKNOWN 按 TRUE 解释为 TRUE，再取否定，也得到 FALSE。

把上面两条再应用一次，还能得到原书式 (5.7)–(5.8)：

> `⌈x⌉⊥ ≡ ¬⌊¬x⌋⊥`
>
> `⌊x⌋⊥ ≡ ¬⌈¬x⌉⊥`

这四条式子的用途不是增加四种新逻辑，而是告诉我们：当一个解释操作向表达式内部移动并遇到 NOT 时，应该把 `⌊·⌋⊥` 换成 `⌈·⌉⊥`，或反过来。

## 一个容易犯错的推导

令 `p` 表示 `amount > 100`，考察 WHERE 中的否定：

```sql
WHERE NOT (amount > 100)
```

WHERE 使用 FALSE interpretation，因此原始语义是：

> `⌊¬p⌋⊥`

按刚才的关系，正确的下推是：

> `⌊¬p⌋⊥ ≡ ¬⌈p⌉⊥`

如果金额为 NULL，`p` 为 UNKNOWN。右侧先把 UNKNOWN 按 TRUE 解释，再取否定，结果是 FALSE；这正是 WHERE 不保留该记录的结果。

错误的写法是把解释方向保持不变：

> `⌊¬p⌋⊥` **不能**直接写成 `¬⌊p⌋⊥`

当 `p` 为 UNKNOWN 时，错误的右侧会先得到 FALSE，再取否定得到 TRUE，反而会保留这条未知金额的记录。三值求值与解释不能被交换成任意顺序。

## 把解释推到比较运算

当解释已经到达会产生 UNKNOWN 的比较谓词时，原书把解释和比较合并成两个新记号。以相等为例：

> `e₁ =⁻ e₂ := ⌊e₁ = e₂⌋⊥`
>
> `e₁ =⁺ e₂ := ⌈e₁ = e₂⌉⊥`

`=⁻` 的结果总是 TRUE 或 FALSE，适合表示 WHERE 中的相等；`=⁺` 也总是二值，但把 UNKNOWN 当作 TRUE，适合对应 CHECK 这类解释。它们都不是上一节的点等号 `≐`：


| 比较      | `NULL` 与 `7` | `NULL` 与 `NULL` |
| ------- | ------------ | --------------- |
| SQL `=` | UNKNOWN      | UNKNOWN         |
| `=⁻`    | FALSE        | FALSE           |
| `=⁺`    | TRUE         | TRUE            |
| 点等号 `≐` | FALSE        | TRUE            |


因此，`=⁺` 和 `≐` 只是在某些输入上恰好相同，定义和用途并不相同。对 `≤`、`≥`、`<`、`>`、`≠`，原书用同样的方法定义 `θ⁻` 和 `θ⁺`。

有些内置谓词本来就不会产生 UNKNOWN，例如 `IS NULL`、`IS NOT DISTINCT FROM`、`EXISTS` 和 `MATCH`。对这类表达式，两种解释都不会改变结果：

> 如果 `b` 只产生 TRUE 或 FALSE，则 `⌈b⌉⊥ ≡ b` 且 `⌊b⌋⊥ ≡ b`。

这给出了一个很实用的停止条件：下推到只产生二值结果的谓词时，不需要继续携带解释记号。

## 这一节留下的规则

现在可以用一句话概括整个过程：

> 解释可以穿过 AND 和 OR；解释遇到 NOT 时必须换方向；到达比较谓词时，可以把解释固化为 `θ⁻` 或 `θ⁺`。

这也是下一节布尔表达式预处理的基础。预处理不能先把 UNKNOWN 随便改成 FALSE，再处理否定；必须先把否定下推，明确每个叶子谓词到底采用哪一种解释。
