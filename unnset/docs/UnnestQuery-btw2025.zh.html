完整翻译摘要

SQL 允许非常灵活的查询嵌套方式，其中也包括访问查询外层属性的子查询。这类相关子查询能够简化查询表述，但执行效率很低，会导致 O(n²) 的运行时间复杂度；对于大型数据库，这种代价可能高到无法接受。

因此，查询优化器会尝试对依赖查询进行去嵌套，也就是去相关。然而，现有去相关技术要么适用范围有限，要么会在相关查询反复嵌套时产生次优执行计划。本文提出一种广义的去嵌套方法：它能够处理深层嵌套的相关子查询，并可推广到包括递归 SQL 在内的复杂查询构造。该方法改善了受影响查询的渐近复杂度，因此可能带来极其显著的性能提升。

关键词：查询优化、查询去嵌套。

压缩导读1 引言

论文从 SQL 的声明式承诺讲起：用户只应描述想要什么，数据库负责选择执行方式；但复杂相关子查询经常让这种承诺失效。图 1 的查询要找出汽车市场中拥有超过 5 个、且收入超过 30 万的订单的客户。查询含两层相关子查询，规范翻译会产生嵌套依赖连接。

依赖连接右侧必须针对左侧每个元组重新求值，复杂度为 Θ(|L||R|)。论文报告，该查询在 PostgreSQL 16、TPC-H SF1 上需要 25 分钟以上；人工把子查询解耦后则能很快完成，但这种改写理应由 DBMS 自动完成。

作者随后回顾 2015 版方法：它不匹配 SQL 文本模式，而是在代数层构造无重复绑定域 D，再把由 D 驱动的依赖连接向下推。该方法已被多个系统采用，但实践暴露出两个缺口：

  1. 递归 SQL、复杂 ORDER BY/GROUP BY 等高级构造没有被完整覆盖。
  2. 多个依赖连接层层嵌套时，自底向上逐个消除会扩大早先步骤的工作量；嵌套越深，问题越严重。

2025 版对应提出两项改进：用整体式、自顶向下的算法联合处理嵌套依赖连接；并补齐递归 SQL、共享 CTE、全外连接谓词和逐绑定 Top-N 等构造。

2 背景

摘要2.1 问题定义

本节沿用 2015 版符号：依赖连接让左侧属性在右侧可见；𝒜(T) 表示表达式 T 产生的属性，ℱ(T) 表示其中尚未绑定的自由变量。若 ℱ(T) 非空，表达式不能独立求值。

L ⧑ R ≡ L ⋈ R　当　𝒜(L) ∩ ℱ(R) = ∅

去嵌套问题因此表述为：给定含依赖连接的关系代数表达式，把它改写成语义等价且不含依赖连接的表达式。

摘要2.2 自底向上去嵌套

这部分是对 2015 算法的重述：

  1. 先尝试简单去嵌套，把只是语法位置造成的相关谓词移动到连接条件。
  2. 若仍有依赖，从外侧投影自由变量的不同绑定，形成无重复域 D。
  3. 把由 D 驱动的依赖连接穿过选择、连接、分组等算子，直到它变成普通连接。
  4. 如果等值条件提供了替代列，可选地用 map 算子消除 D；是否这样做由连接选择性决定。
L ⧑ R ≡ L ⋈natural D (D ⧑ R)，　 D := Π𝒜(L) ∩ ℱ(R)(L)

这个过程概念上能够消除任意依赖连接，但“每次从最深处开始、一次只处理一个连接”的调度策略存在病理情况。

重点翻译2.3 自底向上方法的局限

自底向上方法对大多数查询都工作良好，但会在某些边界情况下退化。最初向作者报告这个问题的是 Sam Arch；他把复杂 UDF 翻译成纯 SQL，在这类查询中，依赖子查询可能像图 1 那样相互嵌套。论文用下面这个缩小后的变体说明问题。为了在小例子中触发缺陷，作者额外加入了相关条件 T3.a = T1.a。

算法首先消除较低的依赖连接。优化器很可能保留下面这个绑定域，而不是做列替换，因为过滤条件 T2.a = T1.a 可能具有较高选择性：

ΠT2.b(σT2.a = T1.a(T2))

问题出现在第二次运行算法、继续消除最上层依赖连接时。此时，较低连接右侧在概念上会针对 T1.a 域与 T2.b 域的完整笛卡尔积求值，而不是只针对 T1 与 T2 实际连接结果中出现的绑定组合求值。

最终结果仍然正确，因为更高处的连接条件会过滤掉不满足 T2.a = T1.a 的 T1.a 组合；但过滤发生得太晚，分组算子已经处理了大量根本不可能进入结果的值。

嵌套越深，这个问题越严重。Sam Arch 提供的真实查询名为 crash.sql，其中包含六层嵌套连接。旧策略产生多个巨大的中间笛卡尔积；这些组合随后虽然都会被过滤掉，却已经消耗了内存和 CPU。这个案例促使作者开发一种同时考虑全部依赖连接的整体式方法，从根源上避免无效域的交叉相乘。

重点翻译3 整体式查询去嵌套

新算法在一次过程中联合处理嵌套依赖连接。它可以看成 2015 方法的自顶向下版本：仍然使用自由变量绑定域 D，但不再把显式的 D 连接逐层穿过代数树，而是在遍历状态中记录“这里最终需要加入哪个 D”，并持续改写算子，直到 D 不再需要或能够安全加入。

算法分为三个部分：

  1. 预处理：识别所有非平凡依赖连接，并记录主算法所需的访问点。
  2. 主过程：按从上到下的顺序消除非平凡依赖连接。
  3. 算子规则：定义选择、映射、分组、窗口、连接等算子如何响应去嵌套状态。

会议论文因篇幅没有给出完整形式化定义和正确性证明，而是将其放在技术报告 A Formalization of Top-Down Unnesting 中。因此，本节是算法说明与伪代码，不应误读成论文内已经完成的形式化证明。

3.1 识别非平凡依赖连接

首先要找出右侧确实访问左侧属性的依赖连接。最直接的实现使用 indexed algebra：对每一次列访问，分别找到访问该列的算子 o₁ 和产生该列的算子 o₂，然后计算两者的最低公共祖先（LCA）。如果 LCA 不是 o₁ 自身，那么这个祖先必然是负责提供该绑定的依赖连接；算法把 o₁ 记录到该连接的 accessing 集合中。

没有访问算子的依赖连接是平凡的，可以直接改成普通连接。Indexed algebra 能在不增加额外数据结构的情况下，以 O(log n) 完成一次 LCA 查询；不支持该能力的系统也能通过维护各子树可用列集合得到相同信息，只是渐近复杂度更差。

3.2 消除依赖连接

识别完成后，算法按从根到叶的顺序处理依赖连接。如果某个依赖连接嵌套在另一个连接之中，通常会在消除祖先连接时一并消除；如果祖先过程提前停止，也可能稍后单独处理。关键约束是：绝不把两个不同的绑定域 D 穿过彼此的依赖连接，从而避免 2.3 节的域笛卡尔积问题。

第一步：广义简单消除

函数 simpleDJoinElimination(join):
  对 accessing(join) 中的每个算子 op：
    如果 op 到 join 的路径是线性的：
      如果 op 是可合并进 join 的选择：
        把选择合并进 join，并从 accessing(join) 删除 op
      否则，如果 op 是能够移到 join 上方的 map：
        把 map 移到 join 上方，并从 accessing(join) 删除 op

  如果 accessing(join) 为空：
    把 join 转成普通连接

  返回是否成功转换

这里的“线性”是指算子允许按输入分区处理。选择可以在条件允许时并入连接；map（有些系统称为 projection）不能简单删除，但可以尝试移到连接上方。如果所有访问点都被移除，依赖连接就变成普通连接。2.2 节的 EXISTS 示例只需要这一步；本文的嵌套示例则不行。

第二步：维护整体式状态

如果简单消除不足，就启动完整算法。状态分为全局不变部分和随当前查询片段变化的部分：

UnnestingInfo:
  join       当前要消除的 L ⧑ R
  outerRefs  右侧读取的左侧列，即 𝒜(L) ∩ ℱ(R)
  D          Π_outerRefs(L)
  parent     外层去嵌套状态（若存在）

Unnesting:
  info       指向共享的 UnnestingInfo
  cclasses   用 union-find 保存列等价类
  repr       outerRefs 到替代列的映射

parent 用于识别当前过程内部遇到的嵌套依赖连接。cclasses 支持传递等价推理：如果已有 a=b 和 b=c，外层引用 c 就可能用当前可见的 a 替换。实际采用的替代关系记录在 repr 中。

函数 rewriteColumns(op, unnesting):
  对 op 中的每一个列引用 c：
    如果 repr 中存在 c：
      用 repr[c] 替换 c

第三步：主消除过程

函数 dJoinElimination(join, parentState, parentAccessing):
  如果简单消除成功：
    若存在父状态：
      按父状态重写被移动的 map
      继续用父状态 unnest 当前连接
    返回

  如果这是嵌套情形：
    取出位于 join.left 中的父访问点
    先用父状态 unnest(join.left)
    重写当前连接条件及被移动的 map

  为当前 join 创建 UnnestingInfo 和局部 Unnesting
  若存在父状态，把位于 join.right 的父访问点并入当前访问集

  把 join.condition 提供的等价关系加入 cclasses
  unnest(join.right, 当前状态, 合并后的访问集)

  对每个外层引用 c：
    向 join.condition 加入
    c IS NOT DISTINCT FROM repr[c]

这个过程首先处理嵌套连接的左侧，再建立当前连接自己的状态，并把仍然落在右侧的父访问点合并进来。最后加入空值安全的相等条件，使改写后的列仍按 SQL 的 NULL 语义与原外层绑定对应。

完整运行示例

  1. 从最外层依赖连接开始，初始化 outerRefs={T1.a}、空的 cclasses 和 repr，并调用 unnest(Γ4, {σ6, σ9})。
  2. 处理 Γ4 时先递归处理输入，返回时再把外层引用加入分组键。随后遇到另一个非平凡依赖连接。
  3. 先处理内层连接的左输入。选择 σ6 提供等价关系 T2.a=T1.a，因此把两列加入同一个等价类，并从访问列表删除 σ6。
  4. 访问列表清空时有两个选择：加入显式域 D:=Π[a:=T1.a](σ[f=123](T1))，或者用等价列 T2.a 替换 T1.a。论文假设 σ2 具有选择性，因此示例选择保留显式域连接。
  5. 随后把父级和当前层需要的外部引用合并为 {T1.a,T2.b}，处理另一侧的 Γ8、σ9 和 T3。为同时展示另一条分支，示例假设优化器这次选择替换，记录 T1.a→T3.a、T2.b→T3.b。
  6. 沿递归栈返回时统一重写列、扩充分组键，并在连接条件中补上空值安全的等值关系。整个过程始终没有构造 domain(T1.a) × domain(T2.b)。

3.3 各类算子的去嵌套规则

所有算子共享两条通用逻辑：

  1. 若调用 unnest(op, state, accessing) 时访问集已经为空，遍历就停止；优化器要么在这里加入 state.D ⋈ op，要么根据 cclasses 用等价列替换全部外层引用。
  2. 递归进入输入时，如果当前算子本身是访问点，就把它从访问集中删除。

选择与 map

unnest(selection):
  把选择谓词中的等价关系加入 cclasses
  unnest(selection.input)
  按 repr 重写选择条件

unnest(map):
  unnest(map.input)
  按 repr 重写 map 的计算表达式

分组与窗口

unnest(groupby):
  static := 分组键为空，或 grouping sets 包含空集合
  unnest(groupby.input)
  重写 groupby 中的列
  把每个 outerRef 的替代列加入分组键
  如果 static：
    用 D LEFT JOIN groupby 包装结果，
    按映射后的 outerRefs 连接

unnest(window):
  unnest(window.input)
  重写窗口表达式中的列
  把每个 outerRef 的替代列加入 PARTITION BY

静态聚合是没有普通分组键的聚合。即使输入为空，它也必须产生一行，因此需要左外连接（或系统支持时使用 group join）保留每个外层绑定。窗口函数同样必须按外层绑定分别计算，所以外层引用要进入 PARTITION BY。

原文 group-by 伪代码中的 groupy 是 groupby 的排印错误，本文已按正确名称处理。

连接

unnest(join):
  把访问点分成左侧访问和右侧访问

  如果 join 本身是另一个非平凡依赖连接：
    调用 dJoinElimination，把父子过程合并
    返回

  如果只有左侧访问外层列，且连接不需保留右侧未匹配行：
    只 unnest 左侧，并重写连接条件
    返回

  如果只有右侧访问外层列，且连接不需保留左侧未匹配行：
    只 unnest 右侧，并重写连接条件
    返回

  否则：
    分别创建左右状态并 unnest 两侧
    按连接类型重写连接条件
    对每个 outerRef 加入
      left.repr[c] IS NOT DISTINCT FROM right.repr[c]
    合并左右两侧的 cclasses 和 repr

连接的列替换必须考虑连接类型：左外连接用左侧代表列，右外连接用右侧；全外连接要逐行判断哪一侧存在，可使用 COALESCE(left.repr[c], right.repr[c])。这也是新算法不能只做机械列改名的原因。

重点翻译4 处理复杂 SQL 构造

第 3 节规则足以处理大多数查询，但全外连接条件中的相关子查询、WITH RECURSIVE、共享 CTE 和 ORDER BY ... LIMIT 都需要额外处理。它们构成 2025 版相对于 2015 版的第二项主要贡献。

4.1 全外连接条件中的相关子查询

SQL 允许连接条件访问连接两侧的列，也允许在任意表达式中放置子查询。因此，连接条件中的子查询可能同时引用左右输入。对于内连接或左外连接，可以把子查询 cross apply 到右输入后正常去嵌套；右外连接可以交换两侧。全外连接更复杂，因为输入随外层绑定变化时，“未匹配元组”应如何计算并不直接明确。

论文的变换分别构造左右输入所需的绑定域 DR 和 DS：

  1. 针对 DR × DS 的每一种可能绑定计算一次子查询谓词，并把结果保存为布尔列 m。
  2. 先用左外连接把 S 接回谓词结果，确保来自 S 的未匹配元组总共只产生一次，而匹配元组按 R 的外层绑定产生。
  3. 再用全外连接接回 R，得到最终匹配行与未匹配行。

实现时不必真的构造整个 DR × DS 子计划再重新去嵌套；可以直接对原子查询调用 unnest，使用稍作修改的 UnnestingInfo 表示组合域，并向两层连接补充对应的 IS NOT DISTINCT FROM 条件。

4.2 去嵌套 WITH RECURSIVE

论文假定递归 CTE 被翻译成 iterate 算子以及读取上一轮结果的 iterationscan：iterate 左侧计算种子，右侧重复执行直到为空。

去嵌套时，递归过程必须针对每一种外层绑定分别执行。为此，把外层引用加入递归 CTE 的列，相当于让递归按这些绑定值分区。算法还把当前递归的全部 iterationscan 加入访问列表，以确保遍历一定抵达这些扫描并给它们补上绑定列。

unnest(iteration):
  把访问点分到种子侧和递归侧
  把当前 iteration 的所有 iterationscan 标为递归侧访问点

  先 unnest 种子侧：
    重写种子输出列
    把 outerRefs 的替代列加入 iteration.leftColumns

  再 unnest 递归侧：
    把 outerRefs 的替代列加入 iteration.rightColumns

unnest(iterationscan):
  对每个 outerRef：
    找到种子输入中对应的绑定列
    把它作为 iterationscan 的新输出列
    更新 repr

先处理种子侧很重要，因为递归侧需要知道新增列及其映射。最终，每个外层绑定都拥有自己独立推进的递归状态。

4.3 去嵌套共享 CTE

共享 CTE 会把代数结构从树变成 DAG。同一个相关选择可能从连接左右两条路径抵达，于是访问列表无法简单地分到左右两侧；若直接按树算法执行，还可能把共享子计划去嵌套两次，重复插入域扫描。

解决办法是把 DAG 切成一组树，使每个共享算子成为独立子树的根，共享读取成为相邻树的叶子。收集访问点时：

  • 如果访问算子和依赖连接在同一棵树中，按普通规则记录。
  • 如果跨越共享边界，就把所有共享读取视为访问点，并继续递归分析共享定义。
  • 指定一个共享读取负责在遍历到达时触发共享定义的去嵌套，其余读取只消费改写结果。

这样，共享部分只改写一次，也只加入一次绑定域。

4.4 去嵌套 ORDER BY LIMIT

相关子查询中的 LIMIT 或 OFFSET 必须针对每一种外层绑定分别执行，不能在去嵌套后变成一次全局限制。Umbra 的排序算子原生支持分区 Top-N；其他系统可以把子查询：

SELECT *
FROM S
ORDER BY x
LIMIT l OFFSET o

改写为窗口查询：

SELECT *
FROM (
  SELECT *,
         ROW_NUMBER() OVER (
           PARTITION BY 外层绑定列
           ORDER BY x
         ) AS rn
  FROM S
) q
WHERE rn BETWEEN o + 1 AND o + l

之后只需由窗口算子规则把外层引用加入 PARTITION BY，就能保证每个绑定拥有自己的排序、偏移和限制。

重点翻译5 评估

查询去嵌套通过消除依赖连接的二次复杂度改善渐近性能。作者指出，只要不断扩大数据集，就很容易制造任意大的加速比，因此传统性能实验的解释价值有限；本节主要展示新算法是否能够避开旧算法的灾难性计划。

压缩导读6 相关工作

早期方法直接在 SQL 表示上匹配特定模式，易于理解和集成，却无法覆盖所有情况。Kim 的早期规则还存在著名的 count bug：空输入上的聚合可能得到错误结果，后来由 Kiessling 修正。此后虽然不断增加特例规则，仍没有形成完整覆盖。

Magic Sets 通过外层绑定域和半连接减少依赖执行工作量，与本文的 D 很相似，但没有给出彻底消除依赖连接的机制；后续方法能消除某些含聚合的依赖连接。作者把 2015 版定位为第一套概念上完整的通用方案，而 2025 版负责修复嵌套连接的计划爆炸，并补齐复杂 SQL 构造。

论文还强调了一个新的现实动机：越来越多 SQL 由程序自动生成。例如 Apfel 可以把过程或 UDF 编译为纯 SQL；这种路线能避免专用过程语言实现，甚至可能更快，但前提是数据库能够可靠地消除生成查询中的深层相关性。

摘要7 结论

2025 版把先前的自底向上去相关扩展为整体式、自顶向下的方法，能够正确联合处理嵌套依赖连接，并覆盖更广的 SQL 构造。该方法已经集成到 Umbra。作者希望 DuckDB、PostgreSQL 等系统后续采用。

与 2015 版的关系

问题2015 版2025 版
