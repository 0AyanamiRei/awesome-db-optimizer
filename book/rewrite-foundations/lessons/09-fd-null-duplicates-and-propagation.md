# L09 · FD、NULL、重复行与算子传播

原文：§6.2–§6.4，印刷页 208，[PDF 第 229 页](../../Query%20opt.pdf#page=229)。§6.2 给出含 NULL 的 FD 定义后留下 `XXX`，§6.3 只有 dependency graphs 的占位文字，§6.4 是文献标题。本节解释原书已经写出的定义，补上理解后续代数所需的最小边界，并明确哪些内容不能归给原书。

## 含 NULL 时为什么换成点等号

第五章已经区分了 SQL 相等 `=` 和点等号 `≐`：

- `NULL = NULL` 的结果是 UNKNOWN；
- `NULL ≐ NULL` 的结果是 TRUE；
- 一个 NULL 和一个普通值用点等号比较，结果是 FALSE。

如果直接用 SQL `=` 定义 FD，前提条件可能得到 UNKNOWN，不能稳定地回答“两条记录在左侧是否相同”。原书因此把含 NULL 的 FD 写成：

> `∀t₁,t₂ ((t₁∈R ∧ t₂∈R ∧ t₁.A₁ ≐ t₂.A₁) ⇒ (t₁.A₂ ≐ t₂.A₂))`

也就是说，判断两个 tuple 的属性集合是否相同时，使用能处理 NULL 的点等号。这里的 FD 语义是：**左侧按点等号相同的记录，右侧也必须按点等号相同。**

例如下面的关系满足 `A → B`：

| `A` | `B` |
| --- | --- |
| NULL | 7 |
| NULL | 7 |
| 1 | 9 |

两行 NULL 在 `A` 上按点等号相同，在 `B` 上也相同。若出现第三行 `(NULL, 8)`，该 FD 就被违反。

## SQL 相等不是可直接收集的等价类

含 NULL 的 FD 与第五章 L06 的谓词等价类有一个重要区别：这里讨论的是**约束定义**，不是 WHERE 对 UNKNOWN 的接受行为。不能看到两个可空列都写成 `A=B`，就直接把它们加入普通等价类。

如果表达式中的比较要服务于 WHERE，需要先经过 `pushnot` 和 `pushunk`，形成 `=⁻` 这样的二值叶子；如果要定义 FD，则必须明确采用原书的点等号语义。两者都能避免把 UNKNOWN 当作普通 FALSE，但它们解决的是不同问题：

| 对象 | 比较规则 | 用途 |
| --- | --- | --- |
| SQL 谓词 `A=B` | 可能为 UNKNOWN | 表达查询条件 |
| `A=⁻B` | UNKNOWN 按 FALSE 解释 | WHERE 中的二值化谓词 |
| FD 的 `A≐B` | NULL 与 NULL 相同 | 定义属性值依赖 |

## FD 不等于“没有重复行”

函数依赖比较的是属性值，不是行的出现身份。考虑一个 bag：

| `id` | `name` |
| --- | --- |
| 1 | Ada |
| 1 | Ada |
| 2 | Lin |

它满足 `id → name`：所有 `id` 相同的行，其 `name` 都相同。但 `id` 不一定是这个 bag 的键，因为完全相同的 `(id,name)` 仍然出现了两次。

因此必须区分：

- **值层 FD**：相同属性值决定相同属性值；
- **行身份或重复约束**：同一组属性值最多对应一次出现。

第七章引入 bag 和 TID 后，这个区别会反复出现。一个 FD 本身不能证明结果是 duplicate-free，也不能单独支持删除一个可能放大重复的 join。

## 原书 §6.3 的传播缺口

原书 §6.3 的标题是“Deriving Functional Dependencies over algebraic operators”，正文位置留下 `XXX dependency graphs`，没有给出完整的依赖图算法或算子规则。因此本教材不把下面内容说成原书已经完成的定理，而只给出阅读后续章节时所需的安全直觉：

1. **选择通常保留已有 FD。** 选择只删除记录，不会让原来相同的左侧值产生新的右侧差异；但选择谓词也可能额外制造新的 FD，例如筛选 `A=1` 后，在结果中可以得到 `∅ → A` 的实例性结论。是否能把它当作 schema 级事实，还要看谓词来源。
2. **重命名只搬运属性名。** 如果 `A→B` 成立，统一重命名后的对应属性仍满足同样结构的 FD。
3. **投影只能保留可见属性上的已知依赖。** 如果投影保留了 `X` 和 `Y`，并且输入有 `X→Y`，这个依赖可以随结果保留；投影删除属性后，不能继续使用引用了被删除属性的 FD。
4. **连接和分组需要按算子语义重新检查。** 输入两侧的 FD、连接谓词、NULL 补值、重复倍数和输出粒度都会影响结果。不能把“左表有键”直接改写成“连接结果中同样没有重复”。

这些规则是教学上的检查入口，不是 §6.3 缺失的完整传播算法。后续第七章学习 projection、join、grouping 和 bag 后，会为每类算子逐一重建证明所需的条件。

## 依赖图应该表达什么

把 `A→B` 画成从 `A` 指向 `B` 的边，可以帮助发现传递链；但图本身不是 FD 的定义。多属性依赖例如 `AC→D` 不能简单画成一条 `A→D` 或 `C→D` 的边，否则会丢失“两个属性必须一起提供”的信息。

对 `R(A,B,C,D)`，若有：

```text
A  → B
B  → C
AC → D
```

图可以帮助看到 `A→B→C`，但只有在闭包中同时拥有 `A` 和 `C` 后，才能使用 `AC→D`。这就是为什么 L08 用属性闭包，而不是只沿着单属性箭头走。

## 第六章的学习接口

读完本章，应当能够区分四层信息：

> FD 定义 → Armstrong 推理 → 键与闭包 → NULL、重复和算子边界

后续遇到一个优化规则时，先问三个问题：

1. 这个 FD 是 schema 保证，还是当前数据碰巧满足？
2. 比较 NULL 时使用的是 SQL `=`、点等号，还是解释后的 `=⁻`？
3. 规则需要的是值层依赖，还是还需要 duplicate-free / 行身份条件？
