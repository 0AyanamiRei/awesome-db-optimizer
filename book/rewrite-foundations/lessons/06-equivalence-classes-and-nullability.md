# L06 · 从相等谓词建立等价类

原文：§5.5–§5.7，印刷页 204–206，[PDF 第 225–227 页](../../Query%20opt.pdf#page=225)。本节先解释相等条件如何支持属性替换，再说明 NULL 为什么迫使我们改用 `=⁻`，最后如实记录 §5.6 Nullability Inference 只有标题。关系、属性和谓词例子是教学展开；原文的具体推导和疑似缺口见[边界记录](../boundaries.md)。

前两节已经建立了两层准备工作：普通值比较在二值逻辑中具有熟悉的相等性质；含 NULL 的 SQL 比较会产生 UNKNOWN，必须先选择 TRUE 或 FALSE interpretation。现在可以回答一个优化器常见的问题：如果谓词中出现 `A = B`，什么时候可以把另一个地方的 `A` 换成 `B`？

## 二值相等为什么能形成等价类

先忽略 NULL，使用普通值比较 `=ᵛ`。它满足：

- 反身性：`A =ᵛ A`；
- 对称性：`A =ᵛ B` 与 `B =ᵛ A` 等价；
- 传递性：`A =ᵛ B` 且 `B =ᵛ C` 时，可以推出 `A =ᵛ C`。

因此，谓词中收集到的相等条件可以把表达式分成若干等价类。例如 `A = B` 和 `B = C` 让 `{A,B,C}` 成为一类。在保持作用域和类型不变的前提下，把这个类中的一个属性名替换成另一个属性名，不会改变二值谓词的结果。

这里的“替换”不是字符串替换。它只作用于谓词表达式的出现位置，必须保持属性可见、类型一致，并且不能捕获嵌套表达式中的同名变量。

## 什么叫“合取出现”

原书先定义一个局部概念：表达式 `e` 在谓词 `p` 中**合取出现**，意思是 `e` 是让 `p` 成立所必需的条件。为此引入一个替换记号：`p[e/false]` 表示把 `p` 中相关出现的 `e` 换成 FALSE，再对结果化简。

在二值语义下，如果：

> `p[e/false] ≡ FALSE`

就说明把 `e` 设为 FALSE 会让整个谓词必为 FALSE；`e` 位于一个真正的合取要求中。实际实现可以通过恒等式和幂等律化简这个结果，而不是枚举所有数据行。

例如 `p = (A = B) ∧ (C > 10)` 中，`A = B` 合取出现，因为把它替换为 FALSE 后，整个 `p` 化为 FALSE。相反，在 `p = (A = B) ∨ (C > 10)` 中，它不是必需条件：即使第一项为 FALSE，第二项仍可能使整体为 TRUE。

## 一个替换如何帮助连接

考虑 `R(A,B)` 与 `S(C)`，以及连接谓词：

```text
A = C OR B = C
```

如果直接执行一个带 OR 的连接，许多高效的等值连接实现无法直接使用。可以先把两种情况拆开：

```text
(R ⋈[A=C] S)
UNION
(R ⋈[B=C AND A<>C] S)
```

第二个分支要求 `B=C` 且 `A<>C`，因此两个分支不会同时接收同一条输入组合。于是可以分别使用等值连接；第二个分支再检查剩余谓词。

在第二个分支中，`B=C` 合取出现，所以在二值逻辑下可以把 `C` 替换为 `B`：

> `B=C ∧ A<>C ≡ B=C ∧ A<>B`

这样 `A<>B` 只引用 `R` 的两列，可以先对 `R` 做选择，再与 `S` 连接：

```text
(R ⋈[A=C] S)
UNION
((σ[A<>B](R)) ⋈[B=C] S)
```

这个例子说明等价类并不是为了漂亮地打印谓词，而是为了把跨关系条件改造成可以提前过滤或使用专门连接算法的形式。

## NULL 让普通 `=` 失去相等关系

SQL 的 `=` 不能直接当作普通的二值等价关系：当任一侧为 NULL 时，结果是 UNKNOWN，因此可空表达式上的“相等”不能无条件提供反身性和可替换性。作为一个三值运算，`x = y` 与 `y = x` 仍会给出相同结果；这里真正失效的是把“结果为 TRUE”当成覆盖所有输入的普通等价类关系。刚才的替换式在三值逻辑下不再无条件成立。

取下面一行：

| `A` | `B` | `C` | `B=C ∧ A<>C` | `B=C ∧ A<>B` |
| --- | --- | --- | --- | --- |
| 3 | 3 | NULL | UNKNOWN | FALSE |

左侧的 `B=C` 和 `A<>C` 都涉及 NULL；合取结果是 UNKNOWN。右侧的 `B=C` 是 UNKNOWN，但 `A<>B` 是 FALSE，整个合取被 FALSE 决定。因此两个原始三值结果不同。

这两个谓词如果放在 WHERE 中，都会被过滤掉，因为 WHERE 只接受 TRUE。于是可以得到上下文中的等价：

> `⌊B=C ∧ A<>C⌋⊥ ≡ ⌊B=C ∧ A<>B⌋⊥`

但如果放在 CHECK 中，左侧 UNKNOWN 会通过，而右侧 FALSE 会违反约束；它们就不再等价。**能够在某个 WHERE 上下文中得到相同接受行为，不等于两个三值表达式本身等价。**

## 为什么收集的是 `=⁻`

L05 说明，先执行 `pushnot` 和 `pushunk`，就能把 SQL 相等的 FALSE interpretation 写成二值叶子：

> `e₁ =⁻ e₂ := ⌊e₁ = e₂⌋⊥`

`=⁻` 无论输入是否为 NULL，都只产生 TRUE 或 FALSE。原书因此使用“合取出现的 `=⁻` 表达式”建立等价类，而不是直接收集原始 `=`：

1. 先确认 `e` 出现在合取要求中；
2. 再要求把 `e` 换成 FALSE 或 UNKNOWN 时，整个谓词都化为 FALSE；
3. 只把满足条件的 `=⁻` 两边放进等价类。

第二个条件保留了三值语义的边界：一个条件如果变成 UNKNOWN 后仍可能让整个谓词保持 UNKNOWN，就不能把它当作普通的 FALSE 条件来做无条件替换。完成 `pushunk` 后，`=⁻` 自身已经没有 UNKNOWN，收集过程才可以安全地使用二值等价的直觉。

这里的安全范围是明确的：这是为 FALSE-interpreted 选择条件服务的等价类。换到 CHECK 或其他 TRUE interpretation，必须重新检查替换是否保持那个上下文的接受行为，不能自动复用同一张类表。

## §5.6 的真实状态：Nullability Inference

原书在 §5.6 只留下 `Nullability Inference` 标题，§5.7 是参考文献；没有给出可连续阅读的定义、规则或算法。因此本教材不能把这一节写成“原书已经完成的 nullability 推导”。为了让后续章节读起来不缺桥梁，下面只给出最小的教学补充：

| 表达式或信息 | 能否产生 NULL / UNKNOWN |
| --- | --- |
| 声明为 `NOT NULL` 的列 | 该列值本身不会是 NULL |
| 普通可空列 | 可能是 NULL，比较它可能产生 UNKNOWN |
| `x IS NULL`、`x IS NOT NULL` | 谓词结果始终是 TRUE 或 FALSE |
| 严格传播 NULL 的算术或函数 | 任一相关输入为 NULL 时，结果可能为 NULL |
| `x = y`、`x < y` | 任一输入为 NULL 时，结果为 UNKNOWN |
| `x =⁻ y`、`x =⁺ y` | 结果始终为 TRUE 或 FALSE |

这张表只表达“哪些结果可能为空”的方向性信息，不是原书缺失的完整推导系统。真正的 nullability inference 还需要规定 schema 元数据、每个函数的 NULL 行为、连接和外连接的补值，以及表达式组合规则。后面遇到这些算子时，会按具体定义重新检查，不能只凭这一张表传播结论。

## 第 5 章主线接口

读完本章，可以把一个谓词的处理过程固定成四步：

> 普通值与 NULL → 三值比较 → 三值逻辑求值 → 上下文解释

需要优化时，再按下面的顺序整理：

> `pushnot` → `pushunk` → 在安全条件下建立 `=⁻` 等价类 → 进行属性替换或谓词下推

这条顺序把三种容易混淆的对象分开了：NULL 是输入值，UNKNOWN 是比较或逻辑的结果，TRUE/FALSE interpretation 是使用上下文对最终结果的接受规则。量词和图 5.2 的剩余规律见[补充课 L06b](06b-quantifiers-and-chapter-review.md)。第 6 章会在这些基础上引入函数依赖；第 7 章则把这些谓词放入 bag、分组、连接和更大的代数表达式中。
