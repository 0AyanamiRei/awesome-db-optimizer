# L05 · 预处理一个布尔表达式

原文：§5.4 Preparation of Boolean Expressions，印刷页 204，[PDF 第 225 页](../../Query%20opt.pdf#page=225)。本节解释 `pareval`、`pushnot`、`pushunk` 的职责和次序。原书只给出处理原则；订单和选择条件是教学展开。这里假设谓词是确定、无副作用的表达式；如果函数可能抛错、修改状态或依赖求值顺序，不能把下面的逻辑推导直接当成执行顺序承诺。

上一节已经得到三条事实：

1. 三值逻辑中的 UNKNOWN 不能直接当成 FALSE；
2. UNKNOWN 的解释可以下推到 AND 和 OR；
3. 解释遇到 NOT 时必须换方向。

优化器在应用更复杂的改写之前，通常先把布尔表达式整理成更容易分析的形式。本节把这个整理过程拆成三个名字。

## `pareval`：已知结果时停止继续判断

`pareval` 是 partial evaluation 的缩写。合取中只要有一个项得到 FALSE，整个合取就已经确定为 FALSE，其他尚未求值的项不再影响逻辑结果；析取中只要有一个项得到 TRUE，也有同样的性质。

例如：

```sql
WHERE amount <= 100 AND status = 'paid'
```

如果某一行的 `amount <= 100` 已经得到 FALSE，整条 WHERE 条件就不会为 TRUE，不需要再根据逻辑结果判断 `status = 'paid'`。在关系代数里，可以把一个包含多个条件的选择看作级联的选择：先应用一个选择，再对保留下来的行应用另一个选择。这样每个条件都能独立参与后续下推。

这只是结果层面的安全条件。真实系统还要考虑表达式是否会抛出异常、是否有副作用、是否允许观察求值顺序；本教材在这里沿用原书的纯逻辑模型，不把 `pareval` 解释成 SQL 对所有函数都必须采用的短路执行保证。

## `pushnot`：先把否定推到谓词附近

`pushnot` 的任务是把 NOT 尽量向下移动，直到它只包住基本谓词。常见步骤包括：

> `¬¬p ≡ p`
>
> `¬(p ∧ q) ≡ ¬p ∨ ¬q`
>
> `¬(p ∨ q) ≡ ¬p ∧ ¬q`

比较运算的否定也可以换成对应的比较：

> `¬(x = y)` 写作 `x ≠ y`
>
> `¬(x > y)` 写作 `x ≤ y`

这里的不等式沿用第 5 章的定义：只要输入中有 NULL，原比较和它的否定仍可能为 UNKNOWN；两个普通值才进入相应的普通比较。因此，这些不是把 NULL 强行变成某个普通值的二值替换。

例如：

```sql
NOT (amount > 100 AND status = 'paid')
```

经过 `pushnot` 后，可以写成：

```text
(amount <= 100) OR (status <> 'paid')
```

此时 NOT 已经不再包住一个复合表达式，后续才有可能对每个比较分别处理 UNKNOWN 的解释。

## `pushunk`：再把 UNKNOWN 的解释推到底部

`pushunk` 的任务是把 `⌊·⌋⊥` 或 `⌈·⌉⊥` 从整个表达式外部向下推，直到遇到基本谓词。L04 的规则给出了 AND/OR 的直接下推：

> `⌊p ∧ q⌋⊥ ≡ ⌊p⌋⊥ ∧ ⌊q⌋⊥`
>
> `⌊p ∨ q⌋⊥ ≡ ⌊p⌋⊥ ∨ ⌊q⌋⊥`

顶部解释也有完全对应的两条式子。真正需要小心的是 NOT。以 WHERE 的 FALSE interpretation 为例：

> `⌊¬p⌋⊥ ≡ ¬⌈p⌉⊥`

如果在 `pushunk` 时忘记交换方向，就会把 `⌊¬p⌋⊥` 错写成 `¬⌊p⌋⊥`。当 `p` 为 UNKNOWN 时，前者是 FALSE，后者是 TRUE；两者在 WHERE 中会做出相反的保留决定。

再看一个完整的小例子。令 `p` 为 `amount > 100`，原式为：

> `⌊¬p⌋⊥`

先执行 `pushnot`，表达式已经只有一个基本谓词的否定；再执行 `pushunk`：

> `⌊¬p⌋⊥`
> `≡ ¬⌈p⌉⊥`
> `≡ ¬(amount >⁺ 100)`

最后一行的 `>⁺` 表示把比较结果中的 UNKNOWN 按 TRUE 解释。它和普通的 `>` 不同，也和点等号不同。金额为 NULL 时，`amount >⁺ 100` 为 TRUE，外层否定为 FALSE，正好表达 WHERE 不保留未知金额。

## 为什么顺序是 `pushnot` 再 `pushunk`

原书明确给出的顺序是：

> `pushnot`：先下推否定；
>
> `pushunk`：再下推 `⌊·⌋⊥` 和 `⌈·⌉⊥`。

原因可以直接从上面的例子看出。如果还没有处理 NOT，就不知道解释操作接下来会遇到什么结构，也容易把 FALSE interpretation 错带过否定。先完成 `pushnot`，每个 NOT 的位置已经固定；再执行 `pushunk`，每次遇到 NOT 都能根据式 (5.5)–(5.8) 换方向。

这不是说 `pareval` 必须在所有实现中排成一个固定的第三步。它描述的是一种可利用的局部确定性；而 `pushnot`、`pushunk` 是本节为了把三值表达式转换到二值叶子谓词而明确规定的核心阶段。

## 到达叶子后的结果

对会产生 UNKNOWN 的比较 `θ`，定义：

> `θ⁻ := ⌊θ⌋⊥`
>
> `θ⁺ := ⌈θ⌉⊥`

对 `IS NULL`、`IS NOT DISTINCT FROM` 等本来只产生 TRUE/FALSE 的谓词，解释操作可以直接消失。于是，一个 WHERE 谓词可以被整理成只含二值叶子谓词的表达式，同时保持原来的 FALSE interpretation；CHECK 则使用相应的 TRUE interpretation。

“整理成二值叶子”并不意味着整个 SQL 已经没有 NULL。NULL 仍然存在于列值中，只是每个比较如何处理它已经被明确编码进 `θ⁻` 或 `θ⁺`。这是后续谓词下推、等价类构造和选择条件分析可以依赖的接口。
