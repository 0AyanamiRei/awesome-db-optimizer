翻译范围：摘要以及第 1–4 节（PDF 物理页 1–15，印刷页 383–397）。

术语约定：unnesting 译为“去嵌套”，de-correlation 译为“去相关”，dependent join 译为“依赖连接”。普通内连接写作 ⋈；论文中的依赖连接是左半边为实心的蝴蝶结，本文用与原字形对应的字符 ⧑ 表示。

摘要

SQL-99 允许在查询内部几乎任何位置使用嵌套子查询。从用户的角度看，嵌套查询可以大大简化复杂查询的表述。然而，与外层查询相关的嵌套查询往往会产生依赖连接，需要采用嵌套循环方式求值，因而性能不佳。

因此，现有系统会采用若干启发式方法对这些查询进行去嵌套，也就是对它们去相关。这些去嵌套技术可以大幅加快查询处理，但通常仅适用于某些类别的查询。据作者所知，当时还没有任何现有系统能够在一般情形下对查询去相关。本文提出了一种能够对任意查询进行去嵌套的通用方法。由此得到的去相关查询可以采用简单得多、也高效得多的求值方式。

1 引言

SQL 查询经常使用子查询来简化查询表述。先来看贯穿全文的示例所采用的模式：

  • students: {[id, name, major, year, ...]}
  • exams: {[sid, course, curriculum, date, ...]}

下面这个嵌套查询用于找出每名学生成绩最好的考试（按照德国的评分制度，数值越低，成绩越好）：

Q1: select s.name,e.course
    from   students s,exams e
    where  s.id=e.sid and
           e.grade=(select min(e2.grade)
                    from exams e2
                    where s.id=e2.sid)

从概念上讲，对于每一个学生—考试对 (s,e)，该查询都会在子查询中判断，这场考试 e 是否是该学生 s 所参加的全部考试中成绩最好的一场。

从性能角度看，这个查询就不那么理想了，因为必须针对每一个学生—考试对重新计算一次子查询。从技术角度看，该查询包含一个依赖连接（dependent join），也就是一种嵌套循环连接，其右侧的求值依赖于左侧的当前值。这类连接效率极低，会导致至少为二次方量级的执行时间。

因此，数据库管理系统（DBMS）会在内部重写该查询，以消除相关性。用 SQL 表示，这种重写大致如下：

Q1': select s.name,e.course
     from   students s,exams e,
            (select e2.sid as id, min(e2.grade) as best
             from exams e2
             group by e2.sid) m
     where  s.id=e.sid and m.id=s.id and
            e.grade=m.best

此时，子查询的求值不再依赖 s 的值，因此可以使用普通连接。要获得良好的查询性能，这类去嵌套至关重要；但现有技术无法处理任意查询。例如，下面这个 SQL 查询就很难去相关。它找出 CS 或 Games Engineering 专业的学生今后应该重考的考试，因为这些考试的成绩比该生本人或其高年级同学所参加考试的平均成绩更差：

Q2:
select s.name, e.course
from   students s, exams e
where  s.id=e.sid and
  (s.major = 'CS' or s.major = 'Games Eng') and
  e.grade>=(select avg(e2.grade)+1 -- 比平均成绩差一个等级
            from exams e2          -- 该平均成绩来自
            where s.id=e2.sid or   -- 本人参加过的考试，
                  (e2.curriculum=s.major and -- 或者
                   s.year>e2.date))           -- 高年级同学参加过的考试

据作者所知，当时没有任何现有系统能够对这样的查询去嵌套。事实上，对这个查询去嵌套确实很困难：标准的去嵌套技术依赖这样一个事实，即查询内部已有的属性可以用来替换由外层查询确定的自由变量。但这里并不满足这一条件，例如 s.year 就无法被替换。

显然，这种复杂相关查询的求值成本会高于较简单的子查询。然而，正如后文将要展示的，即便是这个查询也确实可以去嵌套。我们必须付出额外工作来推导 s.year 和 s.major 的值，但可以在不使用依赖连接的情况下做到这一点；而且这些额外工作的成本以依赖连接本身的成本为上界。大多数查询在去相关之后都会高效得多；在最坏情况下，我们也只需付出相同的连接工作量。也就是说，我们的去嵌套方法绝不会比直接采用嵌套循环求值产生更高的成本；而在绝大多数情况下，它都能显著提升性能，提升幅度往往达到若干数量级。此外，即便在最坏情况下，它也很可能仍然有利，因为消除依赖连接之后便可以采用效率更高的连接实现。因此，与迄今为止已经发表和实现的各种特例处理方法不同，我们的贡献可以视为一种普遍适用于任何嵌套子查询的去嵌套技术。这项通用去嵌套技术已经完整实现于我们的内存数据库系统 HyPer [KN11] 中，读者还可以通过能够可视化最终查询计划的 Web 界面 hyper-db.de 实际体验它。

查询去嵌套通常能够带来极大的性能收益。视具体查询而定，它可以把一个 O(n²) 的算法（嵌套循环连接）替换为一个 O(n) 的算法（在连接键上执行的哈希连接）。此外，在嵌套求值中，依赖侧要针对每个外层元组执行一次；去嵌套后，它只需执行一次。在大型数据集上，通过去嵌套获得 10 倍乃至 100 倍的性能提升并不困难，因此去嵌套是查询编译中的一项关键技术。确实也存在少数更适合嵌套求值的情形，尤其是外侧非常小、内侧又可以通过索引查找进行求值时；但是否这样执行，应该由查询优化器有意识地作出决定，而不应取决于查询采用了何种写法。默认情况下，应当对查询进行彻底的去嵌套。

本文其余部分的结构如下：第 2 节首先定义本文使用的记号；第 3 节给出代数层面的去嵌套变换；第 4 节介绍适用于特殊情形的进一步优化规则，例如能够推断出函数依赖时可采用的规则；第 5 节进行一次“粗略的”性能评估，把若干其他知名 DBMS 与已经集成本文去嵌套技术的 HyPer 系统进行比较。最后，本文回顾相关工作并给出结论。

2 预备知识

在考察去嵌套技术之前，我们先简要回顾关系代数中的若干定义，因为除了基本算子之外，相关记号并未标准化。

首先是普通（内）连接。它可以简单地定义为先做笛卡尔积，再做选择：

T1 ⋈p T2 := σp (T1×T2).

它计算 T₁ 与 T₂ 中所有相匹配条目的组合。大多数 SQL 查询都会使用它，但在存在相关子查询时，这一定义并不足够。对于外层查询的每个元组，都必须重新计算子查询，因此我们把依赖连接定义为：

T1 ⧑p T2 :={ t1∘t2 | t1∈T1∧ t2∈T2(t1)∧ p(t1∘t2) }.

这里，左侧的每个元组都会触发一次右侧求值。我们用 𝒜(T) 表示表达式 T 产生的属性，用 ℱ(T) 表示表达式 T 中出现的自由变量。要对依赖连接求值，必须满足：

ℱ(T2) ⊆ 𝒜(T1),

也就是说，T₂ 所需的属性必须由 T₁ 产生。

需要注意的是，为了简化记号，本文有时会在连接谓词中显式写出自然连接。我们假定查询中出现的所有关系实例都有唯一的属性名，即便它们引用的是同一张物理表；因此：

A⋈B≡A×B.

不过，如果我们两次显式引用同一个关系名，并且要求进行自然连接，那么就要比较名称相同的属性列，并投影掉重复列。例如：

(A⋈C) ⋈p∧natural join C (B⋈C).

这里，最上层的连接既检查谓词 p，也比较来自左右两侧的 C 的各列，并删除两份 C 列中的一份。

对于半连接（⋉）、反连接（▷）以及外连接（左外连接 ⟕、全外连接 ⟗），我们相应地定义它们的依赖版本；同样，左侧的每个元组都会触发一次右侧求值。原论文使用自定义字体表示这些依赖版本：其共同特征是将普通算子代表依赖侧的左半部填黑。为了避免用不准确的 Unicode 字符替代，本文不另造这些四个字形。

除了连接算子之外，另一个重要算子是分组算子：

ΓA;a:f(e) :={x∘(a:f(y)) |x∈ΠA(e)∧ y={z|z∈e∧ ∀a∈A:x.a=z.a}}.

它按照 A 对输入 e 进行分组；e 可以是一张基表，也可以是由另一个代数表达式计算得到的关系。随后，它计算一个或多个以逗号分隔的聚合函数，从而产生聚合属性。如果 A 为空，就只产生一个聚合元组，这与 SQL 中省略 GROUP BY 子句时的情形相同。

通过映射算子，可以计算函数，并由此构造新的属性：

χa:f(e) :={x∘(a:f(x)) |x∈e}.

除此之外，我们还需要常规的关系代数算子：

(σ, ×, Π, ρ, ∪, ∩, \)

使用这些算子，就可以把 SQL 查询翻译成关系代数。

下文经常需要比较属性集合。作为简写，我们把属性比较算子 =A 定义为：

t1=At2 :=∀a∈A: t1.a=t2.a.

除非另有说明，该算子采用 IS 语义，也就是说，它把两个 NULL 值视为相等。

3 去嵌套

含有相关子查询的查询，在最初转换成代数表示时会产生依赖连接，也就是形如下面的表达式：

T1⧑pT2

如前所述，从性能角度看，依赖连接非常不利，因此我们希望消除它们。从根本上说，我们会不断改写代数表达式，直到右侧不再依赖左侧；此时就可以把依赖连接变成普通连接。为此，本文采用下面将要讨论的两种技术。首先尝试简单去嵌套，用来处理仅仅由语法形式造成依赖的情形。如果它不足以消除查询中的嵌套，就使用能够处理任意复杂查询的通用去嵌套框架。

3.1 简单去嵌套

有时，查询之所以包含相关子查询，只是因为用这种方式写 SQL 更简单。TPC-H Query 21 就是一个例子，其中包含类似下面的片段：

select ...
from   lineitem l1 ...
where  exists (select *
               from lineitem l2
               where l2.l_orderkey = l1.l_orderkey)
...

它会被翻译成如下代数表达式。由于论文的依赖半连接使用自定义字形，本文将它转写成 ⋉ᵈ：

l1⋉dep(σl1.okey=l2.okey(l2))

很容易看出，只要把依赖谓词沿代数树上移，就能对这一片段去嵌套，并把依赖半连接转换成普通半连接：

l1⋉l1.okey=l2.okeyl2

一般而言，简单去嵌套阶段会尽可能地把所有依赖谓词沿代数树向上移动。这个过程可能跨过连接、选择、分组等算子，直到到达一个其输入已经能够提供谓词所需全部属性的位置。如果能够到达这样的位置，就可以利用上面的等价关系把依赖连接转换成普通连接。需要注意的是，这次谓词上提纯粹是为了去相关。后续优化仍可能把谓词或其中一部分重新下推，以尽早过滤元组。

3.2 通用去嵌套

谓词移动很容易实现，而且已经足以处理经常出现的简单嵌套查询。因此我们会首先尝试这种方法；但在一般情形下，还需要一种更复杂的方法：第一步，把原依赖连接变成一个“更容易处理”的依赖连接；第二步，把这个新的依赖连接不断下推到查询内部，直到它能够转换成普通连接。

第一步使用如下等价关系：

T1⧑pT2≡T1⋈p∧T1=A(D)D(D⧑T2) D:=ΠF(T2)∩A(T1)(T1)

乍看之下，这个变换似乎没有明显改善查询计划，因为它只是把一个依赖连接换成了一个普通连接加另一个依赖连接。但再看一步，就会发现这个变换非常有用：在原表达式中，可能必须针对 T₁ 的每一个元组计算一次 T₂，调用次数可能达到数百万。第二个表达式则先计算由所有变量绑定组成的域 D，针对每一种不同的变量绑定只计算一次 T₂，然后通过普通连接把结果匹配回 T₁ 的原始元组。如果重复绑定很多，仅此一步就能大幅减少 T₂ 的调用次数。

可以用第一个示例查询说明这一收益。该查询要找出每名学生成绩最好的考试。直接求值会为该生参加过的每一场考试重复计算一次该生的最好成绩：

σe.grade=m((students s⋈s.id=e.sidexams e)⧑Γ∅;m:min(e2.grade)(σs.id=e2.sid(exams e2)))

上述等价规则使最好成绩的计算可以限制为“每名学生一次”，不再针对每一个“学生—考试”对重复计算。也就是说，依赖连接只需在学生编号的投影上执行：

… Πd.id:s.id(students s⋈s.id=e.sidexams e)⧑Γ∅;m:min(e2.grade)(σd.id=e2.sid(exams e2))

图中完整展示了该规则如何作用于查询计划。从某种角度看，这是把信息从连接的外层（左侧）参数横向传递到内层（右侧）参数，从而消除重复求值。因此，这里的投影必须采用真正会消除重复项的集合语义，而不能使用 SQL 那种保留重复项的多重集语义。

更重要的是，我们已经把一个一般的依赖连接变成了一个以集合为左侧输入的依赖连接；这里的集合是指不含重复项的关系。知道 D 不含重复项，有助于继续把依赖连接向查询深处移动。下文假定所有名为 D 的关系都不含重复项，并且后续等价规则只讨论左侧为集合的依赖连接。

不过需要强调的是，这种嵌套查询优化技术仍然保留 SQL 的多重集语义。无论重复项来自基表，还是由查询计算产生，它们都会在优化后的计划中保留下来；只有用于约束嵌套子查询求值工作量的集合 D 不含重复项。如果查询本来就需要消除重复项，例如使用了 DISTINCT，还可以进一步利用这一点，把重复项消除操作向查询计划下推。

依赖连接下推的最终目标，是让右侧不再依赖左侧：

D⧑T≡D⋈T当F(T)∩A(D)=∅

在这种情况下仍然要执行一次连接，但至少可以用普通连接替换效率很低的依赖连接。正如下文将展示的，我们总能到达这一状态。更理想的目标，是利用已有属性替换这个普通连接，从而彻底消除连接；第 4 节将讨论这种优化。

明确了依赖连接下推的起点和目标之后，下面逐一考察各类算子。对选择算子而言，下推非常简单：

D⧑σp(T2)≡σp(D⧑T2)

这个变换看起来可能有些反常，因为通常我们希望下推的是选择算子。但去嵌套变换的关注点并不在此：首先尽可能向下推依赖连接，直到它能通过替换被彻底消除，或者能够转换成普通连接。消除全部依赖连接之后，才重新使用选择下推、连接重排等常规技术优化变换后的查询。

把依赖连接下推穿过另一个连接会复杂一些，因为连接的两侧都有可能依赖 D：

D⧑(T1⋈pT2)≡{(D⧑T1)⋈pT2:F(T2)∩A(D)=∅T1⋈p(D⧑T2):F(T1)∩A(D)=∅(D⧑T1)⋈p∧natural joinD(D⧑T2):其他情况

如果依赖连接提供的值只在其中一侧需要，就把它下推到相应一侧；否则必须在左右两侧各复制一份。这个规则比较保守；连接下方的表达式经常还可以进一步简化，第 4 节会讨论这一点，此处暂时只使用基本下推规则。如果把依赖连接下推到两侧，就必须扩充连接谓词，让左右两侧也按照 D 的值相匹配。相对于原表达式，这种复制不会带来额外的性能损失：两种写法都要分别计算 T₁ 和 T₂ 共 |D| 次。

对于外连接，如果内侧依赖 D，就必须复制依赖连接，否则无法跟踪外侧未匹配的元组。左外连接的规则为：

D⧑(T1⟕pT2)≡{(D⧑T1)⟕pT2:F(T2)∩A(D)=∅(D⧑T1)⟕p∧natural joinD(D⧑T2):其他情况

全外连接必须始终在两侧复制：

D⧑(T1⟗pT2)≡(D⧑T1)⟗p∧natural joinD(D⧑T2)

半连接与反连接也采用类似规则：

D⧑(T1⋉pT2)≡{(D⧑T1)⋉pT2:F(T2)∩A(D)=∅(D⧑T1)⋉p∧natural joinD(D⧑T2):其他情况 D⧑(T1▷pT2)≡{(D⧑T1)▷pT2:F(T2)∩A(D)=∅(D⧑T1)▷p∧natural joinD(D⧑T2):其他情况

把依赖连接下推穿过分组算子时，分组算子必须保留依赖连接产生的全部属性：

D⧑ΓA;a:f(T)≡ΓA∪A(D);a:f(D⧑T)

这一规则再次利用了 D 是集合这一事实。投影算子的行为与分组算子类似：

D⧑ΠA(T)≡ΠA∪A(D)(D⧑T)

最后还剩下集合运算：

D⧑(T1∪T2)≡(D⧑T1)∪(D⧑T2) D⧑(T1∩T2)≡(D⧑T1)∩(D⧑T2) D⧑(T1\T2)≡(D⧑T1)\(D⧑T2)

借助这些变换，每个依赖连接最终要么通过替换被消除，要么被推到某个基关系之前；在后一种情况下，它可以转换成非依赖连接。因此，任意查询中的依赖连接都可以被消除。

这种方法可能引起的一个担忧是：D 由嵌套子查询的全部变量绑定组成，会不会变得非常大？幸运的是并不会。如果原来的嵌套连接是 T₁ ⧑ T₂，那么 |D| ≤ |T₁|。因此，如果对子查询去相关之后，最上层连接是一个把 T₁ 存入哈希表的哈希连接，那么计算 D 最多只会使这个连接的内存用量翻倍；这已经是绝对的最坏情形。如果知道 T₁ 的值没有重复，例如其中包含键，那么甚至可以不物化 D，直接读取该连接的哈希表，从而消除这部分额外开销。作为回报，我们把一个 O(n²) 操作变成了理想情况下的 O(n) 操作，这样的收益完全值得付出上述内存开销。

以图 2 中 Query Q1 的代数翻译为例。该计划使用依赖连接计算嵌套子查询，随后用它产生的属性 m 检查过滤条件。

图 2：Query Q1 的原始计划

σ[e.grade=m]
└─ ⧑
   ├─ students s ⋈[s.id=e.sid] exams e
   └─ Γ[∅;m:min(e2.grade)]

图 3 至图 7 展示了后续变换。首先，把最上层依赖连接改写成一个普通连接，再加一个由自由变量域驱动的依赖连接。接下来，把依赖连接下推穿过分组算子，并按需要扩充分组属性。然后继续把依赖连接下推穿过选择算子，直到它位于表扫描之前。此时右侧已不再依赖左侧，可以把它转换成普通连接。后续优化再把谓词向下推，产生图 7 所示的计划。

图 5 继续把依赖连接下推到选择算子之下。

在很多情况下——本例也是如此——还可以彻底消除与域 D 的连接。如果域的所有属性都通过等值连接与已有属性相连，就可以直接从已有属性推导出域属性。在本例中，连接完成后必然有 d.id = e2.sid，因此可以用映射算子 χd.id:e2.sid 替换与 D 的连接，如图 8 所示。

图 8 中这种替换的优点是查询的两个部分变得完全独立，原嵌套结构不再留下任何痕迹。

不过，替换会产生原元组集合的超集。就这个例子而言，引用完整性很可能会阻止额外元组出现；但一般来说，去掉与域的连接并改用替换，可能产生更大的中间结果，因为连接原本具有的过滤作用也随之消失。这不会影响最终结果，因为这些元组仍会在更高层、原依赖连接对应的位置被过滤掉，但查询运行时间可能受到影响。因此，是否移除这个连接必须由查询优化器决定，第 4 节将继续讨论。

通过替换消除 σd.id=e2.sid 时还需要谨慎。既然 d.id 由 e2.sid 推导而来，看起来似乎可以直接删除这个选择；但只有在 e2.sid 不可为 NULL 时才安全。如果 e2.sid 可能取 NULL，就必须保留这个选择——此时它实际上只是一次非 NULL 检查。

3.5 反连接示例

最后讨论一个依赖反连接示例。SQL 的 ALL 子句会把一个值与某个可能相关的子查询产生的全部值进行比较；依赖反连接可以用来变换这类查询。设有两个抽象关系：

  • R: {[A, ..., X, ...]}
  • S: {[B, ..., Y, ...]}

查询写作：

Q3: select R.*
    from   R
    where  R.X = all (select S.Y
                      from S
                      where S.B = R.A)

显然，不能把这个查询直接翻译成普通的依赖连接；但可以否定比较谓词，并使用依赖反连接。去嵌套优化过程中，依赖反连接可以进一步变换成“普通”反连接：

R▶X≠YσS.B=R.A(S)⇒R▷(X≠Y)∧(S.B=R.A)S

这里 ▶ 表示论文自定义的依赖反连接，▷ 表示普通反连接。

4 优化

简单去嵌套一旦成功，就会彻底消除查询中相关性的所有痕迹。也就是说，得到的代数表达式看起来就像查询原本没有使用相关子查询一样。不过，一般去嵌套需要增加用于计算域 D 的投影，以及与 D 的连接，这会带来一些额外开销。当然，计算 D 通常仍然远胜于嵌套求值，因为计算 D 及其连接只产生一次性开销，而嵌套求值会导致平方级的运行时间。尽管如此，完全消除 D 仍然很有吸引力，而且有时确实可行，前面的示例查询 Q1（见图 8）就是如此。

一般而言，如果能够用子树中原本就存在的值替代 D，就可以消除它。等值连接中经常会出现这种情况。例如，若查询包含表达式 D ⋈[D.a=R.b] R，那么通过查看 R.b 的值，就能知道 D.a 中能够到达原依赖连接的那些可能取值。这里强调的部分很重要：D 当然可能包含 R 中不存在的值，但这些值永远找不到连接伙伴，因此也就永远不会到达原依赖连接。所以，我们可以忽略它们。

要判断能否进行替换，首先必须分析查询树，找出由连接条件和过滤条件所形成的等价类。例如，过滤条件 σ[a=b] 意味着 a 和 b 属于同一个等价类。我们知道，在最终结果中，a 和 b 的值相同，因此可以用 b 替换 a。计算这些等价关系相对直接。外连接可能带来问题，因为它可能使上述例子中的 a 和 b 不再相等；不过，已知最上层与 D 的连接会拒绝 NULL（NULL-rejecting），因此这里不存在这个问题。

确定等价类 C 之后，就可以按照下面的规则判断是否能够进行替换：

D⧑T⊆χA(D):B(T)当∃B⊆A(T):A(D)≡CB.

因此，我们可以不再与 D 连接，而是使用映射算子扩展 T，利用等价属性计算出原本来自 D 的属性值。注意，这一规则成立的前提是 D 是一个集合。还要注意，替换可能增大中间结果：两种表达式之间的关系不是 =，而是 ⊆。基数增大的原因，是失去了与 D 连接时可能具有的裁剪能力。原先只对 T 中能够在 D 中找到连接伙伴的元组计算相关子树，替换后则会对 T 中的每个元组都进行计算。那些没有连接伙伴的元组，只会在查询树更高处、执行原依赖连接的位置被消除，因此中间结果可能更大。

所以，只有当与 D 的连接过滤作用不强时，替换才划算。查询 Q1 就属于这种情况，因此使用替换是一个好选择；但在一般情况下，查询优化器必须比较两种方案的成本，并选择开销更小的一种。对于过滤作用较强的连接，最好保留 D，从而尽早消除元组。
